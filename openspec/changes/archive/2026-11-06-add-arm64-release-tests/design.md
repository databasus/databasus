## Goals / Non-Goals

**Goals:** Make architecture an explicit part of test selection, execution, artifacts and release eligibility. Reuse the existing suites and data assertions. Keep each implementation task verifiable locally and distinguish that evidence from a native hosted run.

**Non-Goals:** Redesign the publication pipeline, introduce another permanent CI workflow, change product support or accept cross-architecture physical backups. The proposal lists the remaining scope exclusions.

## Decisions

### 1. Expand existing test jobs and preserve their dependency barrier

Keep existing suite entry points and job identities. Add architecture to every test matrix, including script tests in their own matrix job, so shell lint runs once. Preserve all existing package and shard selectors. Verify coverage as the Cartesian product of architectures and required suite/group/shard identities, with uniqueness checks and mutation cases that remove an ARM leg or disconnect a release dependency. Keep `fail-fast: false` on every test matrix and retain backend `-race`.

Use the matching Ubuntu 22 Namespace profiles for backend tests: 4 vCPU / 8 GB for the physical, physical API and agent legs, and 8 vCPU / 16 GB for `logical` and `other`. The logical profile and its two-scenario budget limit simultaneous engine load after the observed operation deadlines; this selection does not establish the historical MongoDB timeout's cause. General tests can use the existing Namespace profiles, including the new 4-vCPU ARM profile; browser containers keep their own pinned operating system. Use GitHub `ubuntu-24.04` and `ubuntu-24.04-arm` VMs for rootful Podman and network-filesystem checks. Log the actual architecture and kernel and fail on an architecture mismatch rather than trusting the label alone. Install Podman explicitly where the runner image does not provide it; derive library paths through the system's package architecture instead of hardcoding x86_64.

Apply the two-scenario per-binary limit to every backend group, including `other`, while retaining eight package processes. The ARM `other` failure in run `42185314987` recorded 72.63% CPU pressure over five minutes and 9–18s registration requests while a large-backup fixture exceeded the unchanged two-minute wait. Its previous eight-scenario setting permitted up to 64 concurrent test scenarios across eight Go binaries. Bound these application instances rather than reducing the fixture payload or increasing its wait.

Keep version selection restricted to automatic `main` pushes and dependent on all test matrices, scans and image checks. A matrix job succeeds only when every required leg succeeds. If script tests move, add their new job to this barrier and to the automated transitive-publication checks. Do not add success overrides or develop exemptions. Existing image smoke and vulnerability checks remain native on both architectures. Make the representative pre-release verification-image build native on both architectures as well; keep the publishing matrix and version rules unchanged.

**Alternatives rejected:** A separate ARM-only workflow can drift and fail outside the release barrier. QEMU or forcing amd64 containers would test different binaries. Duplicating all lint and security scans adds work without increasing native test coverage. Removing shards increases contention and hides which slow group failed.

### 2. Transfer one candidate per architecture with explicit identity checks

Expand the existing candidate producer to amd64 and arm64. Include architecture in its image tag, compressed filename and artifact name, for example `databasus-storage-test:<commit>-arm64` and `databasus-storage-test-arm64`. Update every download attempt and every image consumer together. Inspect the loaded image's OS and architecture before scenarios and verify the expected commit-specific tag. Image-producing and consuming matrices may wait for the whole candidate matrix, as GitHub's `needs` operates at job level; neither depends on backend-group completion.

Keep the existing pinned multi-architecture fixture indexes wherever they already provide native variants. Include architecture in uploaded browser failure artifacts. Preserve retry handling for artifact transport, but never use it to repeat a failed test into a passing result. The application candidates remain distinct from the later versioned publication rebuild, as `docs/architecture.md:372` already explains.

**Alternatives rejected:** One artifact name with overwrite enabled creates a cross-architecture race. Rebuilding the app independently in each suite multiplies build cost and loses the shared candidate identity. Consolidating all image-build jobs is unnecessary for the requested coverage.

### 3. Use one explicit unavailable-image policy in preparation and fixtures

Introduce a small test-support policy for the exact `(architecture, image)` exclusions: arm64 with `mysql:5.7` and `mariadb:5.5`. Apply it before starting a fixture and before pulling its image. Keep per-version subtests so a fixture exclusion skips only the corresponding server scenario and prints a reason; unrelated scenarios and container-free unsupported-version tests remain selected.

Keep the exclusion pairs in one small declarative JSON file owned by the test-container package. Embed that file for fixture selection and read the same file from image preparation using a pinned JSON tool. Do not maintain a second shell list or add another executable just to share two exclusions. Policy evaluation accepts an architecture as input for container-free coverage of both branches on the local host; runtime callers supply the actual execution architecture. Normalize the shell and container-engine architecture names explicitly. Tests enumerate excluded pairs, prove amd64 includes both old versions, and prove supported versions and unknown images are not silently excluded. Install every newly used preparation tool explicitly at its repository-pinned version in the affected jobs.

The current source-literal image discovery can remain unless a demonstrated defect requires changing it. Pull failures outside the policy stay fatal. Product engine registries and client bundles are not changed by a server-fixture exclusion.

**Alternatives rejected:** Catching any missing manifest as a skip hides broken tags and authentication failures. Skipping whole engine packages drops valid coverage. Separate shell and backend exclusion lists can disagree.

### 4. Run the browser UI environment natively and retain strict references

Select amd64 or arm64 from the actual execution architecture. Pin the Node archive checksum for each architecture at the same repository-pinned version, use the existing multi-architecture Playwright digest, and pass the matching platform to image build and run. Include architecture and all selected pins in the browser image cache identity. Reject unsupported architectures explicitly.

Keep the current screenshot threshold of zero changed pixels, fixtures, accessibility checks and rendering-readiness waits. First compare native output with the existing references. If native rendering differs, add an explicit architecture namespace for references and create the ARM references only through the documented update command in a native ARM environment. Ordinary runs never update images, borrow another architecture's reference or relax comparison thresholds. Existing amd64 references remain intact unless a reviewed image change requires otherwise.

**Alternatives rejected:** An amd64 browser on an ARM host supplies no native browser evidence. Increasing screenshot tolerance to accommodate platform differences could hide regressions. Automatically accepting the first ARM screenshot would make a failed comparison look successful.

### 5. Preserve native NFS coverage with a pinned fixture

Replace the single-architecture NFS digest with a multi-architecture NFS fixture that preserves the existing export, mount and `root_squash` semantics. Prefer an immutable multi-architecture manifest of an existing suitable server image after checking its entry point and exports. If none provides the existing behavior, build a small repository-owned kernel-NFS fixture from a digest-pinned multi-architecture base and explicitly configure its exports and services. This choice affects fixture packaging only, not suite coverage or product behavior. Readiness must establish an available export, and cleanup remains scoped to the run.

Cover fixture selection, exports, startup failure propagation and cleanup wiring with automated local tests that do not require the host's network-filesystem setup. Actual CIFS and NFS mount results are evidence from the native VM runs, not from those local structural tests.

**Alternatives rejected:** An ARM-only NFS skip contradicts complete filesystem coverage. Emulating the old NFS container does not prove native fixture behavior. Replacing kernel NFS with a userspace substitute without proving root-squash semantics changes what the test establishes.

### 6. Repair failures from evidence and keep the original assertions

Audit all previous-release requests and response shapes against the selected newest release, rather than changing only the first failing sign-up URL. Use that release's actual API for setup, including its membership and configuration rules; use the current API for post-upgrade checks. Keep upgrade coverage for stored secrets, logical restore, physical chains, verification data and released-agent replacement. Existing historical migration assertions remain in their applicable migration tests when a newest release no longer allows constructing a historical state. Do not add route probing, version fallback or reduce the predecessor to an older passing release.

For MongoDB over SSH, collect source and bastion diagnostics and attempt reproduction with `-race` under the logical group's actual concurrency. The original timeout did not recur in local or native repetitions, or in either architecture's fixed-runner parallelism 4/2/4 experiment. The user accepted this investigation with the explicit limitation that the cause remains unestablished. Preserve failure diagnostics and their regression coverage; do not claim a tunnel repair or add a speculative production change. If a later failure establishes a cause, reproduce it at the narrowest observable layer before fixing it. Legitimately insufficient operation budgets may be corrected with evidence; retries, fixed sleeps, serialized unrelated tests and weakened assertions are not fixes.

Further flaky tests or important defects exposed by this work are repaired in the touched path under the existing repair authorization; keep the artifacts aligned with any necessary repair. Avoid unrelated refactoring.

Run the storage-provider package's elapsed-time regression without other test packages or scenarios competing for the runner: execute that package first with `-race -p=1 -parallel=1`, then execute the rest of `other` with its existing budgets. Preserve its 50 ms egress delay, payloads, connection count and 6.4s segment-write limit. Command-level tests require every package exactly once and propagate failures from both stages; a native 32 KiB chunk mutation must still fail the timing assertion. This isolates a measurement rather than changing a storage guarantee.

The composed storage-creation test must wait for the second Save button to be enabled and no longer loading before clicking it through user-event. The Type selector disappearing does not express the Save button's readiness; AntD discards clicks while loading. Preserve the newer input, assigned-ID callback, single creation request and shared wait limits. Native ARM run `42188840075` reached the final callback wait without a callback; local success alone does not establish that the intermittent failure is resolved.

The WAL sample test must separate its first healthy source observation from archive activity. The monitor captures and resets upload counters on each thirty-second tick. A committed WAL row therefore does not imply that the current sample includes that upload, and the first sample can legitimately have zero archive counters. Observe the first source sample and cleared failure, generate WAL, require a later sample with archived segments, then check every archive counter and timing. Generate another write and require a still newer sample with positive source bytes. Increasing a timeout or requiring archive work in the first source sample would preserve the ordering error.

ARM run `42196582836` also exposed a full/incremental lineage mismatch inside two overlapping ordinary browser runs. The initial assertion did not print the observed rows. Preserve its exact equality and the following single-full and recovery checks while adding diagnostic row values and reproducing the failure. Do not wait for the expected lineage or retry a mismatched row: either would hide the state the scenario must reject. The original log cannot establish that incident's exact cause because it lacks the compared row values. The narrower reproduction below establishes a duplicate-request path to the same lineage mismatch; attribution of the hosted incident to that path remains an inference.

A never-run physical schedule is already due once its enabled configuration is saved, even with a future cron. Sending a separate `AUTO` after that save races the scheduled initial full. If its initial full starts before the configuration acknowledgement, `AUTO` requests another full because no completed chain exists yet; if the first full already completed, it requests an incremental instead. The scheduler owns the initial physical full, and wizard completion sends no separate physical backup request. Logical creation retains its explicit first-backup request. Preserve manual physical request queueing outside creation. Add a controlled wizard HTTP test and a real API regression contrasting the scheduled initial full with `AUTO` during that full. These establish the duplicate-request path without asserting that the original hosted log proved its cause.

**Alternatives rejected:** Hiding the SSH test, increasing a deadline without a diagnosis, or retrying the scenario leaves the underlying failure. Updating only the first stale upgrade route risks discovering the next one after another full hosted run. A compatibility layer in production is unnecessary because the observed upgrade failure is in test preparation.

## Risks / Trade-offs

- **More runners and cache use:** The backend matrix grows from nine to eighteen legs. Preserve measured shards and reuse the saved runner profiles, including eight-CPU logical runners. Do not raise concurrency or shorten operation budgets without evidence.
- **A label or available manifest can still be unusable:** Check the actual runtime architecture and keep the MongoDB-compatible Ubuntu selection. Native startup failures stay failures and are investigated.
- **Native screenshots may require ARM references:** Keep the explicit update process and report missing ARM reference evidence instead of accepting it automatically.
- **Network-filesystem and Podman behavior depends on the VM:** Local policy and workflow tests cannot prove native mounts or rootful execution. Preserve separate VM checks and state this limit in the implementation report.
- **A new release can invalidate the upgrade setup again:** The test must still select the newest release. Keep previous/current clients separate and repair against the selected contract without weakening the post-upgrade assertions.
- **Failure diagnostics can contain secrets:** Preserve existing masking for URLs, credentials and process output when improving evidence collection.

## Migration Plan

No application data migration or user configuration change is needed. Implement fixture and harness repairs first, then expand workflow matrices and their local coverage tests, then update `docs/testing.md` and all affected command descriptions. Keep the normal `main` trigger and manual dispatch behavior.

The implementation checklist ends after local checks and mandatory review. The user has separately allowed a temporary verification branch/workflow during implementation. A hosted verification run can then gather native evidence for both architectures without changing release eligibility or publishing artifacts; it is not a task that blocks the local pre-commit boundary. Do not describe static matrix checks, cross-compilation or an amd64 run as a successful native ARM run. Any temporary verification workflow must not remain as a second permanent source of suite selection. Browser recovery preparation requires Docker's `image save --platform` capability to export exactly the server's platform; `docs/testing.md` records that prerequisite.

Rollback is a normal code/configuration revert. The new Namespace profiles contain no running workloads and can remain available; do not remove them or alter unrelated profiles as part of rollback.

This is consistent with resource contention but does not establish that run's cause. - The first native run passed both upgrade suites, agent Docker/Podman checks and browser UI against the same strict screenshot references. Its ARM logical leg failed in MongoDB, MySQL and MariaDB with operation deadlines; unrelated API requests took seconds. The diagnostic repetitions and fixed-runner parallelism 4/2/4 comparisons did not establish the original timeout's cause. The implementation uses existing eight-CPU logical runners and budgets two parallel scenarios per binary on both architectures while retaining eight package processes and `-race`; it changes no operation deadlines or assertions. The repaired WAL restart check directly verifies ownership release and passed repeated local and native execution.
- Read-only Codex consultation supported a runner-concurrency budget as the leading investigation path and found no demonstrated premature tunnel closure. It also identified a stronger WAL shutdown assertion: pause manager passes, keep the old heartbeat fresh beyond the test budget, restart modules and require the ownership row to be released before resuming manager passes. The test then checks the new session and the same single replication slot. This pins shutdown release directly instead of inferring it from a thirty-second wall-clock deadline.
- ARM storage tests exposed unavailable `atmoz/sftp` and `stilliard/pure-ftpd` images. Native Debian-based fixtures preserve real OpenSSH/Pure-FTPd authentication and file transfer instead of excluding these scenarios. Both Dockerfiles join the configuration scan with precise root exceptions for authentication and chroot setup.

Modern VM kernels reject an explicit NFSv2 toggle even when disabling it; NFS startup now explicitly enables v4 and disables v3 without requesting v2. A command regression fails before that repair and passes after it. Debian's Pure-FTPd binary requests `SYS_NICE` and `DAC_READ_SEARCH` at startup, unlike the custom binary in the replaced image; its isolated fixture grants those two capabilities, retains the daemon's session privilege drop, and forwards syslog diagnostics to container output.
- Initial NFS prerequisites attempted to pull the run-local NFS image before it was built, causing both native network legs to fail during CIFS setup. Prerequisites now check only host capabilities; CIFS pulls its own server and NFS builds its own server. A command-level regression rejects the original pull.
- Both hosted browser e2e legs exposed repeated selection of an already-closing Cron menu. The scenario opens the accessible combobox with ArrowDown, waits for its expanded state and selects the visible titled Cron item once inside the popup identified by that combobox's `aria-controls`. This keeps a previous cadence's closing popup out of the selection. AntD's virtualized menu gives the `option` role only to hidden accessibility elements, so the pointer selection targets the visible item. Local lifecycle failures additionally exposed registry timeouts inside the private recovery engine. Each supervisor now exports the pinned source image from the host cache into its run directory; recovery loads it and uses its exact content ID without registry access. Archive-load failure prevents readiness, and the existing run cleanup owns the archive.
- The native recovery recheck exposed a Docker store difference: a containerd-backed host can report a manifest/index ID, while the private legacy engine loads the config ID. Recovery now derives the config ID by hashing the config from the exported archive, and export explicitly selects the Docker server's platform. Unit checks cover both legacy and OCI archive layouts and reject ambiguous configs. A manifest ID is never passed to the private engine as an image ID.

- The verified upgrade predecessor is v3.65.0. Its setup contract uses resource routes, tagged `settings` objects, explicit SFTP authentication methods, paginated response `items` and physical start `kind`. The repaired upgrade suite passed against that release, including restored data, physical-chain/WAL and released-agent checks. The user accepted this diagnostic outcome with the cause explicitly unestablished.
