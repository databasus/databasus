## Context

See proposal.md for why. This section covers only the current state that shapes the approach.

**Server.** `internal/app/routes.go:21-49` mounts every generated server on one `/api/v1` group behind `RequireContractOperation(contract.OpenAPI)` and the users access middleware. The agent routes stay on the plain group (`routes.go:60-61`). They are served by `internal/features/verification/agents/agent_controller.go` and `runs/agent_controller.go` through `RequireAgentAuth` (`agents/middleware.go:28-96`), which works in this order:

1. It parses the agent ID from the path; an ID that is not a UUID gets `401` before the rate limit.
2. It counts the attempt against 10 requests per second per agent ID, through the global `caching.GetRateLimiter()`. That global is the same counter `internal/app/app.go:142-143` builds and installs.
3. It takes the bearer token and authenticates it through the bridge (`features/verification/bridge.go`), which calls `verification.Module.AuthenticateAgent`.
4. It puts the agent into the Gin context and its ID into the logging context.

Every refusal answers `{"error":"invalid agent credentials"}`. The controllers call the five temporary methods of `modules/verification/module.go:62-68`, which `internal/module/module.go:83-127` forwards to the services.

The backup stream answers `410` to every error of `OpenVerificationBackup` (`runs/agent_controller.go:86-91`), including a failed database read or storage open (`verifications/report_service.go:19-36`). The report answers `400` to every error except `ErrVerificationGone` (`runs/agent_controller.go:139-148`), including a database error inside its transaction.

**Agent.** `internal/agent/api/api.go:61-100` builds two `resty` clients: one retries up to three attempts with a 1 to 4 second wait on transport errors and 5xx, the other never retries. The heartbeat and the version check use the first. The claim and the report use the second, because the runner loop and the report budget own their retries (`api.go:83-86`, `api.go:251-290`). The backup stream and the binary download use a plain `http.Client`. The agent reads only the status of an error: `ResponseError.IsGone` and `IsRetryable` (`api/errors.go:28-30`) drive `runner.go:462-470`, and the body only reaches the log. `runner.APIClient` (`runner/interfaces.go:27-31`) and the heartbeater (`heartbeat/heartbeat.go:29`) take the DTOs of `api/dto.go`.

**Memory.** The heartbeat sends `h.capacity.MaxRAMMb / 1024` (`heartbeat/heartbeat.go:118`). `agents.RecordHeartbeat` writes it to `max_ram_gb` (`agents/service.go:159-178`). The user API returns it as `maxRamGb` (`api/openapi.yaml:3069-3091`, `httpapi/agent.go:12`), the frontend shows it only when it is above zero (`VerificationAgentsComponent.tsx:45-46`, `en.ts:1104`), and telemetry sends it as `maxRamGb` (`features/telemetry/dto.go:32-37`, `service.go:198-205`). The claim already sends megabytes (`runs/dto.go:7-12`).

**Generation and checks.** Each server is generated by a `generate.go` with a `//go:generate go tool oapi-codegen` line next to an `oapi-codegen.yaml`. `mise-tasks/backend/check-generated` finds every such config and reads the contract path from its `generate.go`, so a server or client generated from `agent.yaml` is checked without changing the script. `vacuum` lints only `openapi.yaml` (`mise.toml:81`). The response check of the user test client is the private `contractCheckingDoer` of `internal/lib/apiclient/contract_checking_doer.go`. `depguard` already exempts `internal/lib/agentclienttest` from the test-library ban (`backend/.golangci.yml:107`). `apierror.Code` must equal the `ProblemCode` enum of `openapi.yaml` (`internal/lib/apierror/code_test.go:76-130`).

**Release state.** `v3.63.1` is the latest release. All of milestone 12, `verification-module` included, comes after it, so the user API field `maxRamGb` has never shipped. The agent of the previous release sends `maxRamGb` in its heartbeat and reads error statuses only.

The change answers to the root `AGENTS.md`, `backend/AGENTS.md` and `frontend/AGENTS.md`. These rules constrain it: a handler holds no logic and builds no error body; a service returns `lib/apierror` errors with a stable `code`; dependencies arrive through `Deps` and no package-level variable holds one; the agent imports only `lib`, `engines` and the generated agent client; one statement per table and constraint in a migration; a component renders text only by key.

## Goals / Non-Goals

**Goals:**

- One description of the agent protocol, from which the server, the agent's client and the test client are generated, so the two sides cannot drift again.
- The agent routes behind the same guarantees as the rest of the API: a contract guard, `Problem` errors and a test client that checks every response.
- Memory in megabytes from the agent to the screen and to telemetry, without breaking the agent of the previous release.
- No `internal/features/verification`, no temporary agent methods in `module.go`, no `resty` in the agent's production dependency graph.

**Non-Goals:**

- Paths or bodies designed by the `api-design` skill for the agent. See decision 1.
- A contract for `/system/version` or `/system/verification-agent` in the agent's client. See decision 5.
- Changes to the agent's retry, restore, verify or update behavior beyond replacing its HTTP layer.

## Decisions

### 1. The protocol keeps its wire shape, and the contract names its parameters by the rules

`agent.yaml` describes the four operations with the paths the agent of the previous release calls: `POST /agent/verification/{agentId}/heartbeat`, `POST /agent/verifications/{agentId}/claim`, `GET /agent/verifications/{agentId}/{verificationId}/backup-stream` and `POST /agent/verifications/{agentId}/{verificationId}/report`. The request bodies and success responses keep their field names. The heartbeat gains the optional `maxRamMb`, and `maxRamGb` becomes optional with `deprecated: true` (decision 8). The claim answers `200` with the assignment or `204`. The stream answers `200` with `application/octet-stream`, `format: binary` and `Content-Disposition`. The report answers `204`.

A path parameter's name never reaches the wire, so the contract calls the old `:id` `{verificationId}` at no compatibility cost. The literal segments `agent` and `verification` break `databasus-path-plural-nouns` (`api/vacuum.yaml:76`). That rule gets an exception for exactly these paths, with the reason that the agent of the previous release calls them.

The tag of all four operations is `verification`, the module that serves them.

Schema names never reach the wire either, so they follow the glossary and the module's boundary rather than the old DTOs. The claim's response is `VerificationAssignment`, as `verification/module.go:37` already calls it, and the report's body is `VerificationReport`. "Job" in the glossary means a background job of `background.Runner`, so the old name `JobAssignment` does not survive. The wire field `maxConcurrentJobs` stays, because the agent of the previous release sends it.

*Alternatives.* Redesigning the paths by the skill, such as `/verification-agents/{agentId}/heartbeats`, would make the server serve both shapes for one release and delete the old one in the next. That doubles the routes for no gain to users. Keeping `{id}` would add a second `vacuum` exception that protects nothing.

### 2. Agent errors are `Problem` bodies, and only "gone" answers 410

Every agent operation declares `default` with `Problem`. `agent.yaml` has its own `Problem` and `ProblemCode` schemas, with the codes the agent can receive: `invalid_request`, `unauthenticated`, `rate_limited`, `verification_gone` and `internal`. `verification_gone` is a new `apierror.Code` with status `410`. The stream and the report return `ErrVerificationGone` as that code. Validation errors of the heartbeat, the claim and the report answer `400` with `code` `invalid_request` (decision 7). The handlers stay without logic.

`apierror.Hooks.HandleHandlerError` writes any `*apierror.Problem` it finds through `errors.As` as it is (`internal/lib/apierror/hooks.go:37-45`). The services behind the agent operations can meet problems with other codes, so the module's methods that serve the agent translate them before they return, and only the five codes above leave them:

- `agents.Service.RecordHeartbeat` returns `ErrAgentNotFound` (`agents/errors.go:6-10`) when the agent is deleted between its authentication and the update. The heartbeat answers this as `unauthenticated`, the same as a deleted agent, because the agent's credentials are what stopped being valid.
- Opening the backup file can meet `not_found` from the backups module (`backups/internal/logical/legacy_reads_service.go:37-38`) or from the storages module, wrapped with `%w`. A backup is deleted in the same transaction as its verifications (`LogicalBackupsDeleting`), and a storage that holds backups cannot be deleted, so `not_found` here means the backup went away while the stream opened. The stream answers it as `verification_gone`.
- Any other problem from another module becomes an internal error, wrapped with `%v` so `errors.As` no longer finds it, and answers `500` with `code` `internal`.

This fixes two drops of a job on a server failure (Context, `runs/agent_controller.go:86-91` and `:139-148`). It is compatible with the agent of the previous release, because that agent reads only the status, and it already retries 5xx.

`code_test.go` changes from "equals the enum of `openapi.yaml`" to two checks. Every code of either contract exists in Go. Every Go code appears in at least one contract. `verification_gone` therefore lives only in `agent.yaml`, and the frontend dictionaries get no text for a code the interface never receives. The `api-design` skill says that a new code goes into the contract's enum and the frontend's dictionary in the same change (`.agents/skills/api-design/SKILL.md:49`). That sentence is narrowed to codes of `openapi.yaml`, because the SPA never calls `agent.yaml`.

*Alternatives.* Keeping `{"error":...}` and `{"reason":"gone"}` bodies would need a second error writer and a `vacuum` exception for every operation, and would keep the drops. Reusing an existing `410` code is not possible: the only one, `pending_sign_in_not_usable`, means something else. Adding `verification_gone` to `openapi.yaml` too would keep the old test shape, but put a code into the user API that no user operation answers, and the frontend would need translations for it.

### 3. A second route group serves `agent.yaml`, and the module authenticates the agent

`backend/api/api.go` embeds `agent.yaml` as `contract.Agent`. `internal/app/routes.go` builds a second `/api/v1` group with `httpserver.RequireContractOperation(contract.Agent, logger)` and no users middleware, and calls `verificationModule.RegisterAgentRoutes(group, errorHooks)`. The module's `module.go` exposes `RegisterAgentRoutes` instead of the five temporary methods.

The module's `internal/agentapi` package holds the generated strict server, the handler and the authentication middleware. It is a package of its own, because a second strict server generated into `httpapi` would collide with the first on `ServerInterface`, `Problem` and the other generated names. `docs/architecture.md:229` and step 3 of "Contract first" in the `api-design` skill say that a module serves its strict server from `internal/httpapi`; both gain the sentence that a module serving `agent.yaml` does so from `internal/agentapi`. `RegisterAgentRoutes` mounts the generated handlers on a Gin subgroup that carries the middleware. The generated `GinServerOptions.Middlewares` would run too late: the generated wrapper binds the path parameters first and answers a malformed agent ID with `400` before any of them runs (`httpapi/api.gen.go:801-815`). The middleware reads the agent ID from the path and the bearer token from the header, and calls one service method, `agents.Service.AuthenticateAgent(ctx, AgentCredentials{AgentID, Token})`. The method holds the rules and keeps the order of `RequireAgentAuth`:

1. An ID that is not a UUID returns `unauthenticated` without being counted.
2. The rate limit counts the attempt through the `ratelimit.Counter` that the agents service now takes in its `Deps`, as the `users` services take theirs (`users/module.go:136,164,177`), and returns `rate_limited` over the limit.
3. The token is checked as today (`agents/service.go:148-157`) and a refusal returns `unauthenticated`.

Every `unauthenticated` refusal carries one fixed `detail`. The service logs each refusal with its reason and the client's address, which it reads through `httpserver.GetClientIP(ctx)`, as `users/internal/turnstile` does. The middleware writes a returned problem through `apierror.Write`, or puts the agent into the request context under a key private to the package and its ID into the logging context. The handler takes the agent from the context, calls one service method and returns the generated response.

`agent.yaml` declares a bearer `securityScheme` on every operation, so the contract documents the token. The generated server does not enforce it; the middleware does. Its operations carry no `x-access`. The guard's access mark is therefore "signed in", but no middleware on this group reads it.

*Alternatives.* Counting the rate limit in the middleware would put a rule and a service dependency into HTTP code, which `backend/AGENTS.md` keeps in services. Mounting the agent operations on the existing group would put the users access middleware in front of them, and it would answer the agent's token with `401`. Teaching that middleware about agent tokens would make the `users` module know about verification agents. Putting the agent check into `internal/app` would move a rule about the module's data out of the module.

### 4. One response check serves both test clients

`contractCheckingDoer` moves out of `internal/lib/apiclient` into its own test-only package, `internal/lib/contracttest`, which takes the contract router and a `testing.TB`. `apiclient.New` and the new `agentclienttest.New` both use it. `agentclienttest.New(tb, baseURL, token)` returns `agentclient.ClientWithResponses` with the response check and the bearer token on every request. `apptest` gets `NewAgentClient(tb, credentials)`.

The agent cannot use the check itself, because `tools/archlint` keeps `testing` out of the agent binary. So `lib/agentclient` and `lib/agentclienttest` are two packages, as `docs/architecture.md:156` already plans.

*Alternatives.* A copy of the doer in `agentclienttest` would be a second implementation of one check. Exporting the doer from `apiclient` would make the agent's test client import the user API client, and a change to one client would touch the other.

### 5. The agent calls `/system/version` and `/system/verification-agent` by hand

Both paths never change (`docs/architecture.md:235`), and `/system/version` is already an operation of `openapi.yaml`. The server can serve one path from only one contract, so describing it in `agent.yaml` would need a filter at generation and a second, unserved description of the same operation. The agent keeps its two calls on `net/http`, with the retry of decision 6 for the version check. The download controller in `internal/features/system/agent` stays until milestone 13.

*Alternatives.* Generating a second client for the agent from `openapi.yaml` with `include-operation-ids` would add a generated package for two calls whose shape is frozen forever. Describing both in `agent.yaml` is the rejected option above.

### 6. The agent keeps its retry policy in a request doer of its own

`lib/agentclient` is generated with models and the client, and no server. `internal/agent/api` keeps the agent's policy and wraps the generated client:

- The heartbeat and the version check go through `retryablehttp.Client{RetryMax: 2, RetryWaitMin: time.Second, RetryWaitMax: 4 * time.Second}.StandardClient()` from `github.com/hashicorp/go-retryablehttp`, which `backend/go.mod:148` already holds as an indirect dependency and which becomes direct. It retries transport errors and 5xx, as the `resty` client did, and rewinds the request body itself. Its logger is the agent's `*slog.Logger`, which satisfies the library's `LeveledLogger`. It also retries `429`, which `resty` did not; for a heartbeat that waits out the per-agent limit, that is harmless. The claim and the report use a plain `http.Client`, as today.
- Request editors add the bearer token and the no-cache headers of `api/constants.go:25-28` to every request.
- The backup stream calls the plain generated method, which returns `*http.Response`, and returns the body unread on `200`. `ClientWithResponses` would read the whole backup into memory.
- `ResponseError`, `ErrReportGone`, `ErrReportBudgetExhausted`, `NewIdleTimeoutReader` and the report retry with its budget stay. The budget and the binary check timeout (`upgrade/upgrader.go:20`) become fields set by the constructors, which closes the debt row for package-level durations in the rewrite plan.

`runner`, `heartbeat`, `upgrade` and `start` take the generated types, such as `agentclient.HeartbeatRequest`, `agentclient.VerificationAssignment` and `agentclient.VerificationReport`. `api/dto.go` and `api/enums.go` are deleted. `resty` leaves the agent's production dependency graph and becomes an indirect dependency in `go.mod`: the backend's rclone storage provider imports `rclone/backend/all`, whose Proton Drive backend uses `go-proton-api`, which requires `resty`.

*Alternatives.* A retrying doer written by hand would repeat what `go-retryablehttp` already does, with a body-replay rule and a test of its own. Putting the retry into `lib/agentclient` would mix the agent's policy into generated code that tests also use. Retrying with oapi-codegen's response helpers would read the body before the retry decision, and the stream cannot afford that.

Removing or forking rclone to eliminate its indirect dependency on `resty` would change unrelated storage support. This change keeps that dependency and verifies that the agent binary does not import it.

### 7. The heartbeat records the capacity, and the services validate it

The handler converts the generated request into the module's capacity type without logic. `agents.Service.RecordHeartbeat` takes the memory as two optional values, `MaxRAMMb` and the compatibility value `LegacyMaxRAMGigabytes`, and resolves them: megabytes when present, otherwise gigabytes times 1024, otherwise zero.

Today Gin's `binding` tags check the old DTOs, and the generated strict server checks neither `minimum` nor `required`. The services take over every one of these checks and return `invalid_request`:

- a negative capacity value in the heartbeat (`agents/dto.go:10-13`) or the claim (`runs/dto.go:8-11`);
- a report status other than `COMPLETED` or `FAILED` (`runs/dto.go:33`);
- a table statistic of the report with an empty `schemaName` or `name` (`runs/dto.go:28-29`).

*Alternatives.* Resolving the units in the handler would put a rule into code that must hold none. A request-validation middleware against the contract would check `minimum: 0`. No other module uses one, though, and adding it for one group would make this group differ from the rest.

### 8. Megabytes everywhere, and the old field accepted for one release

- **Agent.** The heartbeat sends `maxRamMb: h.capacity.MaxRAMMb` and no `maxRamGb`. An agent always runs the backend's version after its update check, so no newer agent talks to an older backend.
- **Schema.** A migration renames `verification_agents.max_ram_gb` to `max_ram_mb`, widens the column to `BIGINT` so the conversion preserves the full range of stored gigabytes, multiplies stored values by 1024 and adds `CHECK (max_ram_mb >= 0)`. The down migration divides by 1024, restores the `INTEGER` type and renames the column back. A migration test in `backend/migrations` checks the conversion.
- **User API.** `VerificationAgent.maxRamGb` becomes `maxRamMb` in `openapi.yaml`. The field has not been released (Context).
- **Frontend.** The agents list shows `formatBytes(maxRamMb * 1024 * 1024, formatNumber)` through the key `verification.agents.capacity.ram` with the text `{{size}} RAM` in the six dictionaries. The unit symbols stay English, as `formatBytes` documents.
- **Telemetry.** `VerificationAgentEntry` sends `maxRamMb`. The user decided this during exploration, and accepts that the external collector must learn the new field.
- **Removal.** The rewrite plan gets an item in milestone 13: remove `maxRamGb` from the heartbeat of `agent.yaml` and from the service once the release that sends `maxRamMb` has shipped.

*Alternatives.* Keeping the column in gigabytes and converting at the edges would keep the rounding to zero that this change exists to fix. Keeping `maxRamGb` in the user API as a computed value would carry the same loss to scripts and the screen. Keeping telemetry in gigabytes was offered and declined.

### 9. Tests

- **Protocol API tests** in `internal/modules/verification` switch from `CallOldAPI` to `app.NewAgentClient`: `protocol_test.go`, and the agent calls in `agent_health_test.go`, `claim_test.go`, `retry_test.go`, `scheduler_test.go`, `notification_test.go` and `agents_test.go`. An agent ID that is not a UUID goes through a raw `http.Client`, because the contract cannot describe that request.
- **New API tests** cover every scenario of the `backup-verification` delta: the heartbeat in megabytes, the heartbeat of the previous release with only `maxRamGb`, both units and neither, the unknown agent, a negative capacity on the heartbeat and on the claim, an unknown report status and an unnamed table, `410` with `verification_gone` for the stream and the report of a cancelled verification and of one reclaimed by a second agent, and `500` for a backup whose stored file is missing. An `apptest` helper next to `DamageLocalBackup` removes that file, because the API cannot create that state.
- **The user API scenario** "An agent's token on a user operation" already runs in `protocol_test.go:121-130` and moves along with that test.
- **Unit tests of the agent**: `api_test.go` keeps its `httptest.Server` cases for retries, the budget, `204`, `410` and the stream, which the testing skill allows for failures the real backend cannot be made to produce on demand. The heartbeat test checks that `maxRamMb` carries the configured value unchanged.
- **`internal/lib/contracttest`** gets the tests that `apiclient/contract_checking_doer_test.go` and `apiclient_test.go` hold today for the check itself. `agentclienttest` gets a test against an `httptest.Server`: a `410` with a JSON body that is not a `Problem` fails the test with a message that names the operation and the status, and a matching response passes.
- **End-to-end.** `internal/agent/e2e/update_test.go:33,60` assert `MaxRAMMb` equal to `2048` through `apptest.VerificationAgent`. Nothing else in `internal/agent/e2e` changes. The suite does not cover the previous release's heartbeat, because its "older" binary is built from the current code with only `-X main.Version` changed. The API test above covers that.
- **Upgrade test.** `mise run backend:test-upgrade` runs the migration on data of the previous release.

*Alternatives.* Driving the previous release's heartbeat through the end-to-end suite would need a binary of the previous release in the test, which `TestMain` does not build and the suite never needed before.

## Risks / Trade-offs

- [The external telemetry collector does not know `maxRamMb` when the release ships, and drops or rejects the agents' memory] → The proposal marks it BREAKING. The final summary of the change names it as an action outside the repository.
- [The generated client changes the requests in a way the old server would read differently, such as a missing field or a header] → The agent's end-to-end suite runs the new agent against the new server unchanged apart from the memory assertions. The API tests send the previous release's heartbeat. The paths and field names are taken from `api/dto.go` and `api/constants.go` before they are deleted.
- [The contract guard of the agent group refuses an agent ID that is not a UUID with `500` before the authentication answers `401`] → The guard only matches the method and the path template, and does not check parameter formats. The scenario "An agent ID that is not a UUID" pins the `401`.
- [The second route group shares `/api/v1`, and a gin route conflict between the groups appears only at startup] → `internal/app` tests start the server. The agent paths do not overlap any path of `openapi.yaml`.
- [Moving the response check breaks the user API tests in every package] → The check moves with its tests, and the task runs `./internal/lib/...` and one module's API tests before the agent side changes.
- [A `500` for a missing stored file makes the agent retry an unrecoverable job] → The agent retries the stream up to `maxBackupDownloadAttempts` (`runner/runner.go:452-489`) and then fails the job with an error, which the backend's retry rules handle as for any failure. That is better than today's silent drop, which the backend notices only on the next reclaim.

## Migration Plan

1. The release applies the migration at startup: `max_ram_gb` becomes `max_ram_mb` with values multiplied by 1024.
2. Agents of the previous release keep sending `maxRamGb` until their update check. The server stores it in megabytes.
3. Each agent updates itself to the new release and sends `maxRamMb`.
4. The telemetry collector must accept `maxRamMb` before or with this release.
5. The next release removes `maxRamGb` from the heartbeat, as milestone 13 records.

Rollback: an upgrade is one-way, and a binary of the previous release refuses to start on the new schema (`docs/architecture.md:183`). The down migration restores `max_ram_gb` in whole gigabytes, rounding down, and serves development only.
