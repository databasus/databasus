Implementation repairs covered by task 3.4: cancellation of a running stream takes precedence over the resulting storage error; a parent manifest rejected as malformed by PostgreSQL breaks the incremental chain with `MANIFEST_CORRUPTED`; pre-executor incremental failures and restart recovery record `completed_at`; physical source fixtures configure `summarize_wal` in `postgresql.auto.conf` during initialization so API tests can change it with `ALTER SYSTEM` and reload.

Verification repair in task 4.2: the complete WAL package exceeds the 15-minute per-binary limit. Local verification and the review hook run the same three CI shards concurrently in separate processes. The runner preserves failures and waits for every selected shard; review still rejects an unsharded group, `other` and shell syntax. The 900-second per-command and 1800-second total review limits remain unchanged.

Review repairs: helper tests mirror their source files; notification checks drain completed sends and verify one alert across repeated failed sessions in one process; cleanup and restart drain notification deliveries before reusing or closing the database; the moved mTLS fixture pins its tested PostgreSQL base by digest. The shard runner uses `-failfast` to keep the first failure visible in review output.

Repair exposed by task 3.5 verification: the backpressure scenario rotates segments only while the observed queue is below its pause threshold. After each rotation it waits for source-side flush confirmation or the queue threshold, so existing queued WAL cannot cause an extra rotation. It also waits for the resumed receiver to flush the pre-recovery source position before producing more WAL. An empty local queue alone does not show that the receiver caught up. The test retains exact pause and restart counts. Notification API tests wait for every delivery and use category-specific webhooks to preserve both delivery counts and categories.

The slot-advance recovery scenario waits for a failed write of the specific WAL segment it later checks. Any queued segment is insufficient: an earlier segment can arrive before the selected segment is complete, so terminating the receiver at that point can discard the selected partial segment.

The failed-upload recovery scenario records an active catalog claim and waits for that exact ID to disappear after a failed write. A later claim for the same segment is allowed, because immediate retries can keep another claim present continuously.

Full review repair: the shortened-rotation test waits for the initial full backup to complete, records the current source WAL filename, and requires that segment or a later one to be archived within ten shortened rotation intervals. The bound is checked during polling and is far below the production interval. The shard runner also tests rejection of unknown and unsharded group names.

The strengthened rotation test passes with the two-second interval and fails at its twenty-second archive bound when the application is temporarily given the production five-minute interval. The temporary substitution is restored after that check.
