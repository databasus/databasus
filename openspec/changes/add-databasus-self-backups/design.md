## Context

See `proposal.md` for the problem and scope. These existing boundaries determine the implementation:

- Startup opens the internal database and applies migrations before constructing modules (`backend/internal/app/app.go:66`, `backend/internal/app/app.go:83`). Server startup calls that constructor before serving (`backend/cmd/databasus/main.go:92`). Recovery must branch before it, not run as an ordinary settings request.
- The root administrator is recorded independently of the global role (`backend/internal/modules/users/internal/accounts/user_record.go:27`). The frontend currently derives settings access from `ADMIN` (`frontend/src/app/model/useApplicationStartup.ts:212`), which is insufficient for this feature.
- Storage edits use ordinary workspace permissions (`backend/internal/modules/storages/internal/storage/service.go:176`); deletion and workspace teardown share transactional storage removal (`backend/internal/modules/storages/internal/storage/deletion_service.go:22`, `:75`). These edit permissions are explicitly preserved.
- The master key is a separately loaded file (`backend/internal/lib/crypto/master_key.go:32`). Existing stream encryption derives each file's key from the master key and file ID (`backend/internal/lib/crypto/stream_format.go:40`). Recovery needs that ID inside the downloadable archive rather than only in the lost catalog.
- Instance mail already has configuration awareness and delivery (`backend/internal/lib/mailer/instance_sender.go:46`, `:52`). An unconfigured sender skips delivery without returning an error, so alert code must check configuration before recording a sent message.
- Global settings and the existing SMTP instructions/test action are owned by `frontend/src/pages/instance-settings/ui/InstanceSettingsPage.tsx:32` and `frontend/src/pages/instance-settings/ui/MailServer.tsx:15`. Inline storage creation already exists in `frontend/src/pages/databases/backup-config/ui/BackupStorageSelection.tsx:19`.

The design follows `docs/architecture.md` sections Backend layout, Modules, Data, HTTP API, Long-running work, Stored files and Frontend, together with root `AGENTS.md`, `backend/AGENTS.md` and `frontend/AGENTS.md`. Website and README work follows their module rules. The two data-flow exceptions below must be documented in `docs/architecture.md` during implementation: an encrypted staging file for multi-destination Databasus backups, and a pre-migration recovery bootstrap.

Update `docs/glossary.md` in the implementation with the following canonical terms. Use these terms in the interface and documentation and their mapped names in code/API; do not call the existing master key a recovery key or use self-backup/instance archive as additional product terms. Existing machine paths such as the change ID and `instancebackups` module name remain identifiers.

| Canonical term | Code/API name | Definition to add or extend |
| --- | --- | --- |
| Databasus backup | `instancebackups.Backup`, `InstanceBackup`, `instanceBackupId` | An encrypted snapshot of the internal database, distinct from a backup of a user's database. Its file excludes the master key and user-database backup payloads. |
| Databasus backup destination | `instancebackups.Destination`, `InstanceBackupDestination`, `storageIds` | A current selection of one existing workspace storage, with a selection generation; it owns no provider settings or credentials. |
| Databasus backup copy | `instancebackups.Copy`, `InstanceBackupCopy` | A recorded delivery of one Databasus backup to a selected storage; historical copies do not imply a current destination selection. |
| Databasus backup health | `instancebackups.Health`, `InstanceBackupHealth` | Whether selected destinations have sufficiently fresh successful copies; distinct from instance health's local-dependency/job checks and from database healthchecks. |
| Databasus backup incident | `instancebackups.Incident`, `InstanceBackupIncident` | One persistent unresolved protection problem and its system-mail delivery/reminder state; distinct from database notifications sent through workspace notifiers. |
| Recovery pause | `instancebackups.RecoveryState`, `isRecoveryPaused` | A durable restriction on outbound work after recovering Databasus, cleared by root activation only. |
| Schema identity | `SchemaIdentity`, `schemaIdentity` | The migration-bundle digest plus effective applied migration versions defined in decision 4; compatibility permits retired historical entries under that decision's rules. |
| Master key | existing `crypto.MasterKey`, new `/master-key-*` resources | Extend the existing entry to say that this same secret is saved for recovering Databasus and decrypting backup files; export creates no separate recovery secret. |

Alternative rejected: additional product synonyms make the same object look like multiple features and confuse the existing master key with a newly issued credential.

## Goals / Non-Goals

**Goals:** keep ownership in the existing modules; recover from a self-contained encrypted file; separate a dump outcome from each upload and mail outcome; stop recovery from implicitly upgrading or competing with the old instance.

**Non-Goals:** see the proposal's scope exclusions. In particular, startup recovery does not need a browser import API, an external worker or a catalog-reconciliation algorithm.

## Decisions

### 1. Own Databasus backup behavior in one domain module

Add `backend/internal/modules/instancebackups`, exposed only by its `module.go`. It owns configuration, selection rows, runs, per-storage copies, incident/mail state and key-saving acknowledgment. Internal packages separate configuration, archive production/delivery, protection health and recovery. `users` continues to own bootstrap identity and identity proof; `storages` owns provider settings, file reads/writes/deletion and storage editing. `internal/app` wires these modules and recovery startup without moving business rules into handlers or composition.

Use the existing PostgreSQL engine and `lib/process` for the dump/restore tools. Add a narrowly scoped internal-database operation rather than registering the internal database as a user database or disabling `ValidateNotEmbeddedTarget` for ordinary user operations. No module may import another module's `internal` packages.

Alternative rejected: pretending the internal database is a user database would expose forbidden internal access and mix its catalog and notifications into a workspace. Putting everything in `users` or `app` would mix backup lifecycle rules with unrelated ownership.

### 2. Preserve live workspace storages and protect only deletion

Persist selected storage IDs in `instancebackups_destinations` with a restrictive foreign key to `storages`. Include a selection generation so remove/re-add cannot accept a late old upload. Configuration updates lock the singleton configuration and then the involved storage rows in stable ID order. After ordinary authorization, storage deletion keeps its row lock and performs the transactional public `StorageDeleting` notification before checking database-backup references or cleanup; `app` connects the instance-backup subscriber. It refuses an active selection with 409 `databasus_backup_in_use`, including when database backups also use that storage. If there is no current selection, database references cause `in_use`, then pending cleanup causes `cleanup_pending`. The foreign key remains a race backstop, not the only source of a useful message.

Workspace deletion first checks its own databases (`workspace_not_empty`). If empty, check all selected Databasus destinations across the workspace before per-storage reference/cleanup checks, using a workspace-deleting subscription wired before storage teardown. Any selection causes `databasus_backup_in_use`, even when another storage has cross-workspace database-backup references; without a selection those references cause `in_use`, then cleanup causes `cleanup_pending`. Align the existing requirements in both workspace-deletion and storage-file-cleanup deltas with this ordering. Never rely on whichever storage happens to be enumerated first.

Do not add a root-only storage edit guard. Do not copy provider settings. Resolve the current settings for each new delivery attempt through `storages`, and keep the existing transfer constraints unchanged. Show current workspace/name in selection, and record only nonsecret target labels and operation outcomes in history. A connection change can make older remote copies unreachable; expose that as an access/delivery failure rather than claiming migration.

Delivered-copy history uses a nullable storage reference, detached on explicit storage deletion, instead of keeping deletion blocked forever after deselection. Detached rows retain safe historical labels and report unavailable; they have no live download action. Existing database-backup references and pending-cleanup refusal/abandonment rules still apply. Deselecting does not enqueue successful archives for deletion.

Alternatives rejected: copied global destinations create a second credential owner; locking editors out contradicts the agreed product rule; retaining a restrictive historical reference would make the promised deselect-then-delete flow impossible. The owner can instead create an ordinary private workspace.

### 3. Produce once, stage encrypted bytes, deliver independently

Use a custom-format dump of the entire application database, preserving migration history but excluding database-global roles and ownership grants. Create an encrypted local archive with mode 0600 in the configured temporary directory. Stream tool output directly into encryption; never stage plaintext. Check available disk, cap concurrent production to one, and report a full-disk error without publishing a partial archive. This is a documented exception to disk-free normal backup streaming because independent retries must not keep a database snapshot open or rerun a successful dump for every destination.

The new Databasus backup container has a versioned, bounded outer header containing the backup ID and format. Its encrypted plaintext is a framed sequence: one length-bounded `MANIFEST` record (source release, snapshot timestamp and schema identity), bounded `DUMP` records carrying dump bytes, then exactly one `END` record carrying the backup ID, total dump byte length and SHA-256 digest of the concatenated dump bytes. Record types and lengths are unambiguous and bounded. The backup ID supplies the existing stream-encryption file ID. Write `END` only after successfully draining the dump and checking its exit status. Both the manifest and terminal record are authenticated by the enclosing encryption.

Recovery requires the complete `END` record, matching backup ID/length/digest, and exact EOF with no record or byte after it. The existing decryptor alone accepts an encrypted stream cut between chunks, as `openspec/specs/backup-encryption/spec.md` documents; the new container's mandatory terminal record makes such truncation fail validation before import. A cut before `END`, a cut inside it, a wrong digest or appended bytes is an invalid Databasus backup file. A release hint in a filename or sidecar is untrusted; compare the encrypted manifest instead. Preserve existing formats and behavior for user-database backups. The Databasus backup file remains self-contained without sidecars.

Each delivery uses `storages.WriteFile`, consumes its receipt only when the copy is published and uses a fresh remote object name per attempt. Names include an instance namespace and archive ID, separating Databasus backups from database objects and other installations. Sanitized terminal per-target outcomes, byte size and snapshot time are persisted separately from dump production. A successful dump cannot become a total failure because another storage is down.

Use existing clock and background-runner primitives. The default schedule is hourly in UTC with existing recurring-schedule controls and 30-day retention; one schedule applies to all targets. Adding the first current destination requests a run immediately. Retry failed deliveries from the encrypted spool with exponential backoff from one minute to 15 minutes. Retain a spool for at most 24 hours; after that, fail outstanding attempts and let the next dump provide fresh data. A lost spool after restart ends undelivered copies as interrupted and requests a fresh run; published copies remain valid. Remove unreferenced staging files on restart. Manual concurrent start returns `already_running`.

Retention applies per storage and archive namespace, preserves the newest successful copy per current destination, and requests deletion only through the file store. Keep a successful catalog entry unavailable if its storage was explicitly deleted. Never list a pending upload as a recoverable copy. Retention, pending-file cleanup and generation checks must cover crashes, rollback and removal during upload.

Alternatives rejected: streaming a single dump into all destinations couples progress to the slowest storage; rerunning a dump for each upload gives different snapshots and expensive retries; retaining an unencrypted dump or all bytes in memory exposes secrets or scales with catalog size.

### 4. Recover before normal initialization using staged publication

Add optional `RECOVERY_DUMP_PATH` and `RECOVERY_MASTER_KEY_PATH` to `lib/config`; both must be supplied together. These contain paths, not key material. The ordinary server command calls a public recovery bootstrap through `app` after configuration/client-tool validation and before `app.New`. The existing container still starts its private PostgreSQL first. Recovery accepts only an unused application database with no application relations or users. Existing installations are not a recovery target.

Read the master key as exact bytes, preserving existing encryption semantics. Fully validate the Databasus backup file with a bounded-memory pass through all authenticated records, mandatory terminal length/digest and exact EOF. Compare its authenticated release against `Config.AppVersion` and apply the schema-identity comparison below. Any different release, including a patch or newer version, is refused. A `dev` label alone is not compatibility proof. Only after complete validation import the dump records into a separately named staging database through the PostgreSQL engine, using one transaction and failing on any restore error. Do not run current migrations against either the source snapshot or the staging database to make it fit.

Define `schemaIdentity` as `{ migrationBundleDigest, appliedMigrationVersions }`. The bundle digest is lowercase hexadecimal SHA-256 over all carried migration files ordered by filename bytes. Encode each file as its filename's UTF-8 bytes prefixed by their unsigned 32-bit big-endian length, followed by the raw file contents prefixed by their unsigned 64-bit big-endian length. This fixes serialization, file order and content equality. `appliedMigrationVersions` is a sorted unique list: for each migration version use the migration-history entry with the greatest history-row ID, retaining the version only when that entry says applied. Capture it in the same exported database snapshot consumed by the dump. The shared database infrastructure owns reading migration history; the PostgreSQL engine consumes the supplied snapshot without learning application tables.

Compatibility requires exact bundle-digest equality, every carried migration version present in the effective applied set, and no applied version greater than the target bundle's newest version. Extra historical applied versions absent from the current bundle are allowed when not newer than that maximum. They are not compared as if they were files still carried by the target, removed from history or rerun. After staging import, require its effective applied set to equal the authenticated manifest's set and preserve the full imported history. This matches the existing retired-migration allowance in `openspec/specs/internal-database-migrations/spec.md`; it does not require the applied set to equal only the currently carried IDs. Cover an upgraded same-release source with such historical entries, plus same-label development builds with different bundle digests.

Validate the staged schema and normalize runtime state before publication. Use a data-directory recovery lock and journal for preparing, imported, publishing and completed phases. Publish the staged database under the configured application database identity and atomically install the key file. Database and filesystem changes are not one transaction: the journal must make an interrupted publication resumable and prevent normal startup with a mismatched key/database pair. Record an archive identity and completed marker; the same inputs on restart resume the recovered installation rather than import again, while different recovery inputs on a used target are refused. Failed imports discard staging state and preserve the original unused target/key. Refuse concurrent recovery or a second server while publication is unfinished.

The operator flow is: obtain one archive from the remote storage independently, mount it and the separate key file, start the exact source image with those two path settings, sign in, inspect the paused state, confirm the old instance is stopped, then upgrade through the ordinary path if desired. A mismatch error states both releases and this sequence, never an override.

Alternatives rejected: an authenticated restore endpoint would start after migrations; restoring an older snapshot with a newer binary hides recovery inside an upgrade; writing directly into the target leaves partial data on failure; a key value in environment variables is unnecessary when a file can be mounted.

### 5. Keep recovered work paused until explicit activation

Persist pause independently of runnable schedules, and preserve it across restart and ordinary upgrades. `app` supplies the persisted recovery state through a small domain-neutral execution gate to the background runner and effectful API services. This gate is distinct from a root-only UI check: manual backup/restore/verification starts, storage test writes, outgoing notifier tests, remote cleanup and agent claims cannot bypass it. Wire and test every outbound-effect entry point. Authentication and its explicitly requested confirmation emails, inspection and root activation remain possible.

Normalize in staging: end running backup/restore/verification rows as interrupted; revoke sessions, download/action credentials and verification-agent credentials; clear leases and local-work claims; invalidate local-storage availability until a check on the new host. Discard source-instance unfinished-write/deletion obligations rather than replaying potentially stale cleanup on remote storages, record that discard for root inspection, and explain that leftover files may need manual cleanup. Do not remove completed user-backup catalog rows. A copied Databasus backup run that contains its own in-progress row is interrupted like other in-progress work.

After root activation, retain configured schedules, require physical configurations to begin a new FULL and safely recreate their per-database replication resources under the existing engine rules. Existing completed FULL/INCR/WAL catalog remains usable for downloads to coverage at the snapshot. Re-enroll verification agents because their tokens were revoked. No step promises discovery of files created after the snapshot or repair of remote files already deleted since it.

Set every recovered local storage's additive `recoveryValidationStatus` to `REQUIRES_VALIDATION`. The existing storage views and Databasus backup outcomes expose its unavailability. After root activation it still refuses backup writes, backup reads/downloads/restores and file cleanup with `storage_unavailable`; healthy remote destinations continue independently. The existing saved connection-test operation is the only permitted local-location read/write probe while unavailable. Viewers retain diagnostic access to it, but their success never changes availability. A successful probe by an authorized storage editor changes status to `AVAILABLE` only if the saved settings have not changed since the probe began; failure retains unavailability and a sanitized reason. This narrow exception to connection tests changing no persisted state is defined in the storages delta and changes no settings or secrets. The interface distinguishes connectivity from editor-authorized recovery validation. The probe itself stays blocked during recovery pause. A successful location check says nothing about missing historical files: their individual reads still fail as missing. Test this separately from the instance-wide pause so activation cannot silently enable a lost local destination.

Alternatives rejected: restoring disabled flags into every config loses the owner's intended schedules; pausing only schedulers allows manual writes and cleanup; automatically replaying source leases/deletion requests or continuing the old physical chain can damage surviving remote state.

### 6. Keep root authorization and key proof on the server

Expose an additive current-user `isRootAdmin` capability, derived from the persisted bootstrap designation, for presentation. Services still ask `users` to verify current root identity; do not authorize from a client flag or from the global role alone. Keep `x-access: admin` on the new authenticated API operations and apply the stricter root check in their services.

Have `users` validate the current password or a purpose-bound email code, with rate limits and expiration, without exposing password hashes. Email proof supports OAuth-only accounts when SMTP and a usable account address exist. Otherwise show host-file instructions. Export proofs are consumed for one key download, expire after five minutes and bind to account/session/purpose. The browser first acknowledges an HTTP warning, then confirms identity, then requests a single-use download token expiring after 60 seconds. Do not request key bytes or a usable download token merely to open onboarding or a warning. Require the HTTP acknowledgment in an insecure export request too; derive browser security from the actual page and configured API origin, accounting for HTTPS proxy termination without trusting arbitrary forwarded headers.

Serve exactly the current master key bytes as an attachment with `Cache-Control: no-store`. No settings schema contains the key. Implement a narrow existing-master-key export exception beside the Fields secret-response rule in `.agents/skills/api-design/SKILL.md`, as the API-contract specification requires for intentional departures. The exception names only `GET /master-key-downloads`, authorized by a token issued through `POST /master-key-exports`, and permits that root-admin attachment download only after recent purpose-bound identity confirmation, with expiring single-use authorization, no-store and secret-free audit; it does not permit exporting saved storage/database/notifier secrets or embedding the key in JSON. Document the same exception in the contract and security architecture. This is the one necessary agent-instruction convention change in this feature. Audit proof issuance/export and acknowledgment without proof, token or key values. A keyed acknowledgment is stored by a hash identifying the current key; a download does not set it automatically.

Alternative rejected: a raw key in settings, a reusable signed URL, or a normal `ADMIN` check exposes the instance's decryption root. Requiring SMTP for all exports would unnecessarily block password owners on offline installations; adding new OAuth reauthentication flows is unnecessary with the host-file fallback.

### 7. Use one protection state with independent mail delivery

Persist `NOT_CONFIGURED`, `INITIALIZING`, `HEALTHY`, `PARTIAL`, `FAILED`, `OVERDUE`, `STOPPED` and `RESUMING` as Databasus backup health, with per-target detail. Per destination, persist `outstandingDueAt`, the earliest due schedule occurrence not covered by a successful copy with `snapshotAt >= outstandingDueAt`. Its fixed overdue deadline is `outstandingDueAt + 15 minutes`. New cron occurrences, polls, retries and schedule edits do not advance or erase it. On successful delivery, cover all occurrences up to that copy's snapshot time; choose the earliest later already-due occurrence as the new outstanding one, or leave none until the next due time. A stale snapshot delivered late cannot satisfy a newer occurrence. Schedule edits affect only future occurrences while an outstanding deadline remains. With a five-minute schedule and no successful backup from 12:00, the checker reports overdue at 12:15, not 15 minutes after an endlessly moving latest occurrence.

The checker does not require a failure callback. Configuration writes that remove the last destination create a stopped Databasus backup incident in that same transaction, irrespective of database counts or setup deferral. Configuring the first destination requests a run and starts initializing/resuming; at least one fresh successful copy ends stopped protection, while remaining failed destinations retain partial protection.

Store incidents and mail-attempt timestamps in the module. A background job sends through `mailer.Sender` to the current root-admin email, checking `IsConfigured` and a syntactically usable recipient first. Different symptom updates of one unresolved incident do not generate an email per retry; accepted reminders are at most daily. Failed sends retry exponentially from one minute to one hour, with safe last-error state. A first send becomes eligible when previously missing SMTP/address is supplied. Resolve obsolete pending mail before dispatch. Exactly-once SMTP delivery is not promised after a crash between acceptance and recording it.

Floating notices always reflect active problems, even when SMTP accepted mail. Initial setup reminders alone wait for any user database or storage anywhere in the instance, can be deferred for 24 hours and are suppressed while the settings section is visible. A new stopped incident overrides setup deferral. SMTP absence is its own inline configuration hint and links to the existing mail-server heading; SMTP settings remain operator-owned. Automatic incident mail is suspended during recovery pause.

Alternatives rejected: workspace notifiers require another selection/permission flow; email-only warnings disappear when SMTP fails; alerts emitted only by a failed job miss jobs that never started; email on every attempt floods the owner.

### 8. Define the contract and compose UI through existing boundaries

Add user-API operations tagged `instancebackups`; no agent API change is needed. The intended surface is:

| Resource/action | Behavior |
| --- | --- |
| `GET/PUT /instance-backup-settings` | root-only schedule, retention and selected storage IDs; 200 acknowledged config; invalid/duplicate IDs fail atomically |
| `GET /instance-backup-statuses` | root-only health, current incident, SMTP/address eligibility, key acknowledgment and recovery pause |
| `GET /instance-backup-destinations` | root-only cursor-paged searchable choices across workspaces, safe storage summaries |
| `POST/GET /instance-backups` | 202 start and cursor-paged history, newest snapshot then ID |
| `GET /instance-backups/{instanceBackupId}` | run and per-copy outcomes |
| `POST /instance-backups/{instanceBackupId}/download-tokens` | request one short-lived token for a successful copy |
| `GET /instance-backup-downloads?token=...` | public only by single-use archive-download token |
| `POST /master-key-confirmations` | request a purpose-bound email proof when needed |
| `POST /master-key-exports` | submit password/code proof and get a single-use key-download token |
| `GET /master-key-downloads?token=...` | public only by single-use key-export token; attachment and no-store |
| `PUT /master-key-acknowledgments` | explicit saved-current-key acknowledgment |
| `PUT /instance-backup-reminders` | persist setup deferral only |
| `POST /instance-recoveries/{instanceRecoveryId}/activate` | root confirms old instance stopped; 200 activated recovery state |

All operations declare `Problem`, 401 for no session, 403 for a non-root authenticated actor, validation 400 and state conflicts 409 where applicable. Token downloads use no session in the URL and reject consumed/expired/wrong-purpose credentials. Add `databasus_backup_in_use`, `recovery_paused`, `storage_unavailable` and any identity-proof refusal codes to both contract and dictionaries. Expose recovered local-storage validation status through the existing storage schemas and reuse their connection-test action. All other secrets remain write-only. Regenerate code before handlers, and keep handlers to one service call.

Keep the settings view within `pages/instance-settings`. Add a reusable `features/create-workspace` interaction by extracting the existing app-owned form, letting both app and settings compose it without page-to-app imports. Reuse `features/edit-storage` and the existing multiple/searchable `ResourcePicker`. Cross-screen status/key onboarding belongs in a focused widget with a domain API facade in `entities/instance-backups`; `app` composes it and supplies navigation. No business rules move to shared UI or app-shell. Give SMTP and backup headings stable anchors, scroll the existing settings scroll owner, and move focus to the heading while respecting reduced motion. Persist drafts through inline creation, keep errors beside the failed step and invalidate status immediately after mutations. Session-scoped queries must discard old-session responses and cancel polling on unmount.

Update all seven interface dictionaries together and exercise live locale changes, keyboard interaction, narrow layouts and enlarged text. Translated product text stays in dictionaries. The HTTP warning appears before any proof/key network operation and initial key onboarding takes priority over storage reminders.

Alternatives rejected: a second settings route interrupts the single-page task; importing an app-owned dialog into a page breaks the layer direction; rebuilding storage controls creates a second provider form to maintain.

## Risks / Trade-offs

- Shared storage editors can redirect future encrypted Databasus backup files or make older copies unreachable -> preserve this explicitly accepted policy, explain it during selection and let the owner use an ordinary private workspace. API access to the key and archive remains root-only.
- An encrypted staging file consumes disk proportional to catalog size -> produce only one archive at a time, check space, fail visibly, bound retention of temporary files and clean interrupted spools. Never stage plaintext.
- Database publication and key installation are separate operations -> journal and gate normal startup until a matching pair is fully published; test interruption in every publication phase.
- Exact release labels can be overridden by an operator, and development labels repeat -> check authenticated release and schema identity; document recovery only from trusted images/archives, not as a sandbox for attacker-supplied database dumps.
- Restored catalogs lag remote storage and discarded stale cleanup can leave objects behind -> expose snapshot time and local-storage validation, preserve only the claimed coverage, and document manual cleanup/reconciliation limits.
- Ordinary SMTP cannot guarantee unique delivery around a crash -> persist attempts, bound retry/reminder frequency and retain in-app state; do not promise exactly once.
- An entirely stopped process cannot report its own failure -> document external health monitoring separately without introducing it into this feature.

## Migration Plan

1. Add the instance-backup tables and structural constraints with no selected destinations. Existing installations keep their storage permissions and normal startup. Introduce master-key onboarding on their next authenticated visit.
2. Implement the archive and pre-migration recovery path before presenting a claim that completed archives are recoverable. Exercise successful same-version recovery, refusal and interrupted publication with real PostgreSQL and remote storage.
3. Enable configuration, delivery, retention and incident APIs, then the settings/key/reminder UI. No background backup runs until destinations are selected. Keep the Docker entrypoint's ordinary path unchanged when recovery inputs are absent.
4. Update `docs/glossary.md` with the canonical definitions above; update `docs/architecture.md`, recovery documentation, FAQ/security/SMTP pages and the root README installation advice with all six translations. Replace the exploratory cross-version suggestion with the exact-release procedure, explain separate storage credentials/master key, and keep the manual whole-directory option with its different coverage. Update `docs/testing.md` for the recovery-cycle suite and commands. Update only the necessary master-key export exception in the API-design skill; ordinary feature details remain in feature documentation rather than agent instructions.
5. Run the selected checks in `tasks.md` and finish for automatic proposal/implementation review at their respective boundaries. No commit, push or deployment is part of implementation completion. After migrations have run, use the existing forward-upgrade policy rather than suggesting binary rollback on the same schema.
