## Context

See `proposal.md` for the problem and scope. These existing boundaries determine the implementation:

- Startup opens the internal database and applies migrations before constructing modules (`backend/internal/app/app.go:66`, `backend/internal/app/app.go:83`). Server startup calls that constructor before serving (`backend/cmd/databasus/main.go:92`). Startup recovery must branch before it. A UI request can prepare recovery on a running installation, but publication must happen outside that application's lifetime.
- The newer-schema refusal currently recommends starting the newer image without explaining a deliberate fresh start on an older release (`backend/internal/app/app.go:36`). The documented Docker run and Compose examples bind-mount `./databasus-data` (`README.md:163`, `README.md:191`); the image also declares a data volume (`Dockerfile:182`), so a run without an explicit mount receives an anonymous volume.
- Serving clears the ordinary temporary directory (`backend/internal/app/server.go:31`). Shutdown drains work with a time limit and returns without closing the application database (`backend/internal/app/server.go:74`, `backend/internal/app/app.go:359`). The container stops PostgreSQL and exits when the backend exits (`docker/start.sh:686`). UI recovery therefore needs explicit quiescence, connection closure and application reinitialization; neither a successful shutdown return nor a Docker restart policy proves this has happened.
- The root administrator is recorded independently of the global role (`backend/internal/modules/users/internal/accounts/user_record.go:27`). The frontend currently derives settings access from `ADMIN` (`frontend/src/app/model/useApplicationStartup.ts:212`), which is insufficient for this feature.
- Storage edits use ordinary workspace permissions (`backend/internal/modules/storages/internal/storage/service.go:176`); deletion and workspace teardown share transactional storage removal (`backend/internal/modules/storages/internal/storage/deletion_service.go:22`, `:75`). These edit permissions are explicitly preserved.
- The local provider's ordinary connection test creates and removes an empty file only in `TempFolder` (`backend/internal/modules/storages/internal/providers/local/provider.go:196`). Backups are published to `DataFolder` (`provider.go:123`), so recovery validation must additionally test that directory rather than treating the existing temporary-file check as proof of backup access.
- The master key is a separately loaded file (`backend/internal/lib/crypto/master_key.go:32`). Existing stream encryption derives each file's key from the master key and file ID (`backend/internal/lib/crypto/stream_format.go:40`). Recovery needs that ID inside the downloadable archive rather than only in the lost catalog.
- Instance mail already has configuration awareness and delivery (`backend/internal/lib/mailer/instance_sender.go:46`, `:52`). An unconfigured sender skips delivery without returning an error, so alert code must check configuration before recording a sent message.
- Global settings and the existing SMTP instructions/test action are owned by `frontend/src/pages/instance-settings/ui/InstanceSettingsPage.tsx:32` and `frontend/src/pages/instance-settings/ui/MailServer.tsx:15`. Inline storage creation already exists in `frontend/src/pages/databases/backup-config/ui/BackupStorageSelection.tsx:19`.

Website and README work follows their module rules. Document encrypted backup/recovery staging, the pre-migration recovery bootstrap and the application lifecycle for UI publication in `docs/architecture.md` during implementation.

## Goals / Non-Goals

**Goals:** keep ownership in the existing modules; recover from an encrypted archive and separate master key through either mounted startup files or UI file import; separate a dump outcome from each upload and mail outcome; stop recovery from implicitly upgrading or competing with the old instance.

**Non-Goals:** see the proposal's scope exclusions. Neither recovery path discovers remote files or restores directly from a history entry. UI import needs no external worker, Docker socket or catalog-reconciliation algorithm.

## Decisions

### 1. Own Databasus backup behavior in one domain module

Add `backend/internal/modules/instancebackups`, exposed only by its `module.go`. It owns configuration, selection rows, runs, per-storage copies, incident/mail state and key-saving acknowledgment. Internal packages separate configuration, archive production/delivery, protection health and recovery. `users` continues to own bootstrap identity and identity proof; `storages` owns provider settings, file reads/writes/deletion and storage editing. `internal/app` wires these modules and recovery startup without moving business rules into handlers or composition.

Use the existing PostgreSQL engine and `lib/process` for the dump/restore tools. Add a narrowly scoped internal-database operation rather than registering the internal database as a user database or disabling `ValidateNotEmbeddedTarget` for ordinary user operations. No module may import another module's `internal` packages.

Alternative rejected: pretending the internal database is a user database would expose forbidden internal access and mix its catalog and notifications into a workspace. Putting everything in `users` or `app` would mix backup lifecycle rules with unrelated ownership.

### 2. Preserve live workspace storages and protect only deletion

Persist selected storage IDs in `instancebackups_destinations` with a restrictive foreign key to `storages`. Include a selection generation so remove/re-add cannot accept a late old upload. Configuration updates lock the singleton configuration and then the involved storage rows in stable ID order. After ordinary authorization, storage deletion keeps its row lock and performs the transactional public `StorageDeleting` notification before checking database-backup references or cleanup; `app` connects the instance-backup subscriber. It refuses an active selection with 409 `databasus_backup_in_use`, including when database backups also use that storage. If there is no current selection, database references cause `in_use`, then pending cleanup causes `cleanup_pending`. The foreign key remains a race backstop, not the only source of a useful message.

Workspace deletion first checks its own databases (`workspace_not_empty`). If empty, check all selected Databasus destinations across the workspace before per-storage reference/cleanup checks, using a workspace-deleting subscription wired before storage teardown. Any selection causes `databasus_backup_in_use`, even when another storage has cross-workspace database-backup references; without a selection those references cause `in_use`, then cleanup causes `cleanup_pending`. Align the existing requirements in both workspace-deletion and storage-file-cleanup deltas with this ordering. Never rely on whichever storage happens to be enumerated first.

Do not add a root-only storage edit guard. Do not copy provider settings. Resolve the current settings for each new delivery attempt through `storages`, and keep the existing transfer constraints unchanged. Show current workspace/name in selection, and record only nonsecret target labels and operation outcomes in history. A connection change can make older remote copies unreachable; expose that as an access/delivery failure rather than claiming migration.

Delivered-copy history uses a nullable storage reference, detached on explicit storage deletion, instead of keeping deletion blocked forever after deselection. Detached rows retain safe historical labels and report unavailable; they have no live download action. Existing database-backup references and pending-cleanup refusal/abandonment rules still apply. Deselecting does not enqueue successful archives for deletion.

Alternatives rejected: copied global destinations create a second credential owner; locking editors out contradicts the agreed product rule; retaining a restrictive historical reference would make the promised deselect-then-delete flow impossible. The owner can instead create an ordinary private workspace.

### 3. Produce once, stage encrypted bytes, deliver independently

Use a custom-format dump of the entire application database, preserving migration history but excluding database-global roles and ownership grants. Create an encrypted local archive with mode 0600 in the configured temporary directory. Stream tool output directly into encryption; never stage plaintext. Check available disk, cap concurrent production to one, and report a full-disk error without publishing a partial archive. This is a documented exception to disk-free normal backup streaming because independent retries must not keep a database snapshot open or rerun a successful dump for every destination.

The new Databasus backup container has a versioned, bounded outer header containing the backup ID and format. Its encrypted plaintext is a framed sequence: one length-bounded `MANIFEST` record (source release, snapshot timestamp and schema identity), bounded `DUMP` records carrying dump bytes, then exactly one `END` record carrying the backup ID, total dump byte length and SHA-256 digest of the concatenated dump bytes. Record types and lengths are unambiguous and bounded. The backup ID supplies the existing stream-encryption file ID. Write `END` only after successfully draining the dump and checking its exit status. Both the manifest and terminal record are authenticated by the enclosing encryption.

Recovery requires the complete `END` record, matching backup ID/length/digest, and exact EOF with no record or byte after it. The existing decryptor alone accepts an encrypted stream cut between chunks, as `openspec/specs/backup-encryption/spec.md` documents; the new container's mandatory terminal record makes such truncation fail validation before import. A cut before `END`, a cut inside it, a wrong digest or appended bytes is an invalid Databasus backup file. A release hint in a filename or sidecar is untrusted; compare the encrypted manifest instead. Preserve existing formats and behavior for user-database backups. The Databasus backup file remains self-contained without sidecars.

Each delivery uses `storages.WriteFile`, consumes its receipt only when the copy is published and uses a fresh remote object name per attempt. Names include an instance namespace and archive ID, separating Databasus backups from database objects and other installations. Sanitized terminal per-target outcomes, byte size and snapshot time are persisted separately from dump production. A successful dump cannot become a total failure because another storage is down.

Use existing clock and background-runner primitives. The default schedule is hourly in UTC with existing recurring-schedule controls and 30-day retention; one schedule applies to all targets. Adding the first current destination requests a run immediately. Retry failed deliveries from the encrypted spool with exponential backoff from one minute to 15 minutes. Retain a spool for at most 24 hours; after that, fail outstanding attempts and let the next dump provide fresh data. A lost spool after restart ends undelivered copies as interrupted and requests a fresh run; published copies remain valid. Remove unreferenced staging files on restart. Manual concurrent start returns `already_running`.

Retention applies per storage and archive namespace, preserves the newest successful copy per current destination, and requests deletion only through the file store. Keep a successful catalog entry unavailable if its storage was explicitly deleted. Never list a pending upload as a recoverable copy. Retention, pending-file cleanup and generation checks must cover crashes, rollback and removal during upload.

Alternatives rejected: streaming a single dump into all destinations couples progress to the slowest storage; rerunning a dump for each upload gives different snapshots and expensive retries; retaining an unencrypted dump or all bytes in memory exposes secrets or scales with catalog size.

### 4. Share staged recovery between startup files and UI import

Add optional `RECOVERY_DUMP_PATH` and `RECOVERY_MASTER_KEY_PATH` to `lib/config`; both must be supplied together. These contain paths, not key material. The owner can place both files in the mounted data volume, for example `/databasus-data/recovery/backup.dbbackup` and `/databasus-data/recovery/master.key`. The ordinary server command calls a public recovery bootstrap through `app` after configuration/client-tool validation and before `app.New`. The existing container still starts its private PostgreSQL first. A new startup recovery accepts a fresh application database or an automatically initialized target containing no user accounts, user data or user-changed settings. Existing tables alone do not make the target ineligible.

Recognize automatic initialization by its contents under the existing migration history, without applying migrations to classify the target. Permit migration records, unmodified default singleton settings and automatically generated local files such as the target master key, instance identity, logs and temporary files. Require all user-owned collections to be empty, including accounts (even a sole root account), invitations, workspaces, databases, storages, notifiers, backup history and outstanding work. Default singleton rows, including backup configuration, must match their release's initialization values. Unknown schemas, unexplained persisted content, non-default settings or inability to establish this baseline refuse recovery without changing the target. The target's newer-schema refusal remains in force even if its data otherwise appears automatic. Domain owners supply their checks through public boundaries; neither `app` nor recovery imports other modules' internals. Under exclusive lifecycle access, check eligibility before preparation and again immediately before publication so another server or console command cannot create user state between the check and replacement.

An owner may therefore start Databasus normally, stop it before creating an account or changing settings, add the two source files to the same mounted volume, configure both paths and restart the exact source release. A pre-existing automatically generated target key does not have to match the source key: preserve it on failure and replace it with the exact supplied key only during successful journaled publication. Merely adding files to a running container does not trigger recovery. If user state exists, preserve it and direct the owner to confirmed UI import or a separate fresh target.

UI recovery starts from the root-only Databasus backups section of an initialized installation. On a fresh deployment the owner first creates the temporary root account, then imports an archive file and the source installation's separately saved master-key file from the computer. Both files are required even for an archive previously downloaded from this installation. Do not fetch the archive from a history row or storage, and do not assume the target's current key decrypts it. The target's current root identity authorizes replacement; imported accounts determine sign-in afterward.

Both paths copy their inputs into a private recovery directory outside `TempFolder`, preserving exact key bytes and keeping the archive encrypted. Compute lowercase hexadecimal SHA-256 over the entire encrypted archive file, including its outer header; this archive fingerprint is distinct from the authenticated dump digest. Hash, validate and import the same immutable staged file so changes to an operator's source file cannot change the bytes being applied. Fully validate all authenticated records, mandatory terminal length/digest and exact EOF in bounded memory. Compare the authenticated release against `Config.AppVersion` and apply the schema-identity comparison below. Any different release, including a patch or newer version, is refused. A `dev` label alone is not compatibility proof. Only after complete validation import the dump records into a separately named staging database through the PostgreSQL engine, using one transaction and failing on any restore error. Do not run current migrations against either the source snapshot or staging database to make it fit.

Define `schemaIdentity` as `{ migrationBundleDigest, appliedMigrationVersions }`. The bundle digest is lowercase hexadecimal SHA-256 over all carried migration files ordered by filename bytes. Encode each file as its filename's UTF-8 bytes prefixed by their unsigned 32-bit big-endian length, followed by the raw file contents prefixed by their unsigned 64-bit big-endian length. This fixes serialization, file order and content equality. `appliedMigrationVersions` is a sorted unique list: for each migration version use the migration-history entry with the greatest history-row ID, retaining the version only when that entry says applied. Capture it in the same exported database snapshot consumed by the dump. The shared database infrastructure owns reading migration history; the PostgreSQL engine consumes the supplied snapshot without learning application tables.

Compatibility requires exact bundle-digest equality, every carried migration version present in the effective applied set, and no applied version greater than the target bundle's newest version. Extra historical applied versions absent from the current bundle are allowed when not newer than that maximum. They are not compared as if they were files still carried by the target, removed from history or rerun. After staging import, require its effective applied set to equal the authenticated manifest's set and preserve the full imported history. This matches the existing retired-migration allowance in `openspec/specs/internal-database-migrations/spec.md`; it does not require the applied set to equal only the currently carried IDs. Cover an upgraded same-release source with such historical entries, plus same-label development builds with different bundle digests.

Validate the staged schema and normalize runtime state before publication. A recovery directory has mode 0700 and its files mode 0600. Store the lock, journal, staged encrypted archive and staged key outside the imported database and ordinary temporary-directory cleanup. The journal records the operation ID, origin (`STARTUP` or `UPLOAD`), archive fingerprint, safe manifest fields, target publication generation and phases `PREPARING`, `IMPORTED`, `PUBLISHING` and `COMPLETED`. Never store key bytes or identity proofs in journal metadata. Atomically replace and sync journal records and sync relevant filesystem changes before advancing phases.

Publish the staged database under the configured application database identity and atomically install the key file. Database and filesystem changes are not one transaction: retain the previous target database/key pair until the new pair and recovery pause are durably published. Before publication, failures discard only staged state and preserve the active installation. Once publication starts, the journal makes each step resumable and blocks normal application initialization until a matching pair is selected. Mark completion only after the imported database, exact source key, normalized runtime state and recovery pause are durable. Then release obsolete databases, keys and input copies; retain the safe completion record. Refuse concurrent recovery or a second server while publication is unfinished.

Keep completed startup archive fingerprints in the local journal across subsequent UI imports; do not derive them from snapshot history or only from the most recent recovery. On a normal start first resolve unfinished publication and verify the journal's current database/key generation. A configured archive whose fingerprint was successfully consumed by startup recovery is then skipped before target-eligibility and archive-version checks. This lets the same files and path settings remain configured across restarts and later ordinary upgrades, without rolling back UI imports. A different fingerprint on a target with user state is refused, including different bytes at the same path. Renaming identical archive bytes does not trigger another import. An unfinished operation resumes by its ID and fingerprint rather than starting again. A fresh explicit UI import can deliberately apply the same archive again; retrying the apply request for one operation never publishes it twice.

The startup operator flow is: obtain an archive independently, put it and the separate key file in a mounted volume, start or restart the exact source image with the two path settings on a fresh or automatically initialized target, sign in, inspect the paused state, confirm the old instance is stopped, then upgrade normally if desired. A mismatch error states both releases and this sequence, never an override.

#### Newer-schema refusal and deliberate storage reset

Keep the existing refusal before migrations for both the server and console commands, including both migration timestamps and the instruction to restart the newer image to preserve the installation. Add an explicitly destructive alternative: to use an older image, first save any needed Databasus backup, master key and local backup files outside the storage being deleted, remove the current container and its data, then recreate the deployment with the selected older image. This starts a fresh installation; it neither downgrades the database nor makes a newer-release archive compatible with the older release. Never perform cleanup automatically or offer a schema-check bypass.

Print these separate examples in the refusal and recovery documentation. `databasus` is the example container name; replace it with the deployment's actual name. Run the bind-mount example from the deployment directory and replace its path if another host directory is mounted. `<data-volume>` is a placeholder for the actual named volume, not a command to copy unchanged.

| Data storage | Cleanup commands, in order |
| --- | --- |
| Documented bind mount `./databasus-data:/databasus-data` | `docker rm -f databasus`, then `sudo rm -rf -- ./databasus-data` |
| Named Docker volume mounted at `/databasus-data` | `docker rm -f databasus`, then `docker volume rm <data-volume>` |
| No explicit mount, with the image's anonymous data volume | `docker rm -f -v databasus` |

Explain that `docker rm -v` does not delete bind-mounted directories or named volumes, and that a Compose deployment must be stopped before the same storage-specific cleanup and recreated using its edited image tag. Recreate only the Databasus deployment with its original ports and intended mount configuration and the explicitly selected older image tag. Do not suggest global prune commands. These examples cover the supplied embedded-database deployment; if `DATABASE_DSN` points to an external database, removing the Docker data volume does not reset that database, and the owner must configure a separate empty application database for a fresh start. The diagnostic cannot reliably discover the host bind-mount path from inside the container, so label examples instead of claiming to identify the operator's storage automatically. Already published older images keep their existing diagnostics; this change improves the versions that include it.

Alternatives rejected: requiring no application tables blocks recovery after a harmless first launch; checking only whether accounts exist could erase manually changed settings or other data; a recovery-file presence check cannot authorize overwriting user state. Calling deletion a downgrade conceals data loss, and one generic volume-removal command does not cover bind mounts, named volumes and anonymous volumes.

#### UI upload, confirmation and application lifecycle

Stream the two multipart file parts into private staging with bounded memory, no plaintext dump staging and no filesystem paths supplied by the browser. Add `RECOVERY_MAX_ARCHIVE_BYTES` with a 10 GiB default and a positive-value configuration check; enforce that limit while streaming, including when content length is absent or false. Limit the key file to 64 KiB and require the existing minimum valid key length. Permit one pending upload/preparation or publication per instance. Refuse excessive uploads or insufficient disk space, remove incomplete files after disconnect/failure and expire unconfirmed prepared imports after one hour. Keep journal-referenced publishing files across restart; recovery staging must never be removed by `Serve`'s ordinary temp cleanup. Failed or cancelled preparation releases its staging database and key. A restart before apply invalidates unfinished preparations without replacing the active installation; accepted publication resumes from its journal.

After upload, return 202 and expose validation/import progress through the recovery resource. The active installation remains usable while the staged archive is checked and imported. A ready resource exposes only authenticated snapshot time/source release, archive fingerprint, running release and sanitized status, never the key or decrypted dump. Show the replacement warning and require explicit confirmation plus a new purpose-bound password/email proof before apply. The proof expires after five minutes and binds to the current root account/session, recovery operation and immutable archive fingerprint. Do not reuse a master-key export proof. OAuth-only roots without a password or usable mail proof use mounted-file startup recovery into a separate fresh target, preserving the current account-bearing installation. On HTTP, require acknowledgment before uploading either file; the UI recommends a protected connection or the mounted-file path, and cancellation sends no file bytes.

Apply is a durable asynchronous handoff, returning 202 before stopping the old HTTP service. Record accepted apply intent in the journal before responding; a crash before `PUBLISHING` must still distinguish accepted apply from an unconfirmed preparation. `instancebackups` owns recovery rules and journal transitions; `app` coordinates lifecycle through that public boundary. Block new state-changing requests and console commands, new job passes and agent work. Cancel and drain existing requests, runs, outbound deliveries and loops, and close all application database connections before publication. Use a lifecycle lock shared by normal server/console execution and exclusive publication, so another process cannot mutate the target during replacement. All entrants check durable apply intent under this lock before normal initialization; changing from shared to exclusive access after drain must not admit a new writer. Refuse publication if any work or connection cannot be proven stopped within the drain budget; a timeout is not successful quiescence. Before publication, such a failure retains the old database/key and permits restarting the old application with a visible failure result.

Run publication under the outer command lifetime, not a request context or the module group being drained. After completion the same backend process rebuilds its application/module graph, reloads the installed master key and logging, and serves the restored installation paused. The embedded PostgreSQL stays running. Do not exit the backend expecting Docker to restart it. OS stop signals still follow ordinary container shutdown; any interrupted publication is resolved from the journal at the next start. UI polling tolerates temporary unavailability, drops the old session on 401 and directs the owner to sign in using accounts from the snapshot. Neither a disconnected request nor a reachable version endpoint proves recovery succeeded. After sign-in, the durable recovery state supplies the result and activation controls.

Alternatives rejected: direct recovery from history needs another archive-selection/storage-access path and does not cover files from a lost server; assuming the current master key fails on a newly initialized target; publishing inside the request handler leaves live modules attached to the replaced database; a process exit depends on deployment restart policy. Restoring an older snapshot with a newer binary hides recovery inside an upgrade; writing directly into the target leaves partial data on failure; a key value in environment variables is unnecessary when a file can be mounted.

### 5. Keep recovered work paused until explicit activation

Persist pause independently of runnable schedules, and preserve it across restart and ordinary upgrades. `app` supplies the persisted recovery state through a small domain-neutral execution gate to the background runner and effectful API services. This gate is distinct from a root-only UI check: manual backup/restore/verification starts, storage test writes, outgoing notifier tests, remote cleanup and agent claims cannot bypass it. Wire and test every outbound-effect entry point. Authentication and its explicitly requested confirmation emails, inspection and root activation remain possible.

Apply the same conservative recovery semantics to both entry paths, including a UI import on the same host. Normalize in staging: end running backup/restore/verification rows as interrupted; revoke sessions, download/action credentials and verification-agent credentials; clear leases and local-work claims; invalidate local-storage availability until a check on the target host. Discard source-instance unfinished-write/deletion obligations rather than replaying potentially stale cleanup on remote storages, record that discard for root inspection, and explain that leftover files may need manual cleanup. Quiesce the replaced installation's cleanup worker before publication and do not carry its obligations into the recovered snapshot. This is the explicit lost-server recovery procedure referenced by the storage-file-cleanup delta even when the UI target is initialized. Do not remove completed user-backup catalog rows. A copied Databasus backup run that contains its own in-progress row is interrupted like other in-progress work.

After root activation, retain configured schedules, require physical configurations to begin a new FULL and safely recreate their per-database replication resources under the existing engine rules. Existing completed FULL/INCR/WAL catalog remains usable for downloads to coverage at the snapshot. Re-enroll verification agents because their tokens were revoked. No step promises discovery of files created after the snapshot or repair of remote files already deleted since it.

Set every recovered local storage's additive `recoveryValidationStatus` to `REQUIRES_VALIDATION`. The existing storage views and Databasus backup outcomes expose its unavailability. After root activation it still refuses backup writes, backup reads/downloads/restores and file cleanup with `storage_unavailable`; healthy remote destinations continue independently. The existing saved connection-test operation is the only permitted local-location read/write probe while unavailable. Viewers retain diagnostic access to it, but their success never changes availability. A successful probe by an authorized storage editor changes status to `AVAILABLE` only if the saved settings have not changed since the probe began; failure retains unavailability and a sanitized reason. This narrow exception to connection tests changing no persisted state is defined in the storages delta and changes no settings or secrets. The interface distinguishes connectivity from editor-authorized recovery validation. The probe itself stays blocked during recovery pause. A successful location check says nothing about missing historical files: their individual reads still fail as missing. Test this separately from the instance-wide pause so activation cannot silently enable a lost local destination.

For a recovered local storage awaiting validation, extend that saved connection-test action with a probe of the actual backup directory `DataFolder`, in addition to the ordinary `TempFolder` check. The storages module owns this provider-specific capability; recovery callers do not access local paths directly. In the actual backup directory, create a uniquely named probe containing non-empty bytes, read and verify those bytes, then remove it. Require all steps to succeed before an editor can mark the storage `AVAILABLE`, and attempt cleanup after any failed step. Touch no existing backup file and change no storage settings or secrets. Ordinary connection tests outside recovered-storage validation keep their current behavior. A writable temporary directory with a missing or inaccessible backup directory reports failure and keeps `REQUIRES_VALIDATION`; it cannot pass solely because the existing temporary-file probe succeeds. A viewer may run the extended check but still cannot change availability. Add module/API coverage for this split-directory failure, successful actual-directory validation and unchanged encrypted settings.

Alternatives rejected: restoring disabled flags into every config loses the owner's intended schedules; pausing only schedulers allows manual writes and cleanup; automatically replaying source leases/deletion requests or continuing the old physical chain can damage surviving remote state; checking only `TempFolder` can approve recovered storage whose actual backups cannot be read or written.

### 6. Keep root authorization and key proof on the server

Expose an additive current-user `isRootAdmin` capability, derived from the persisted bootstrap designation, for presentation. Services still ask `users` to verify current root identity; do not authorize from a client flag or from the global role alone. Keep `x-access: admin` on the new authenticated API operations and apply the stricter root check in their services.

Have `users` validate the current password or a purpose-bound email code, with rate limits and expiration, without exposing password hashes. Email proof supports OAuth-only accounts when SMTP and a usable account address exist. Otherwise show host-file instructions. Export proofs are consumed for one key download, expire after five minutes and bind to account/session/purpose. The browser first acknowledges an HTTP warning, then confirms identity, then requests a single-use download token expiring after 60 seconds. Do not request key bytes or a usable download token merely to open onboarding or a warning. Require the HTTP acknowledgment in an insecure export request too; derive browser security from the actual page and configured API origin, accounting for HTTPS proxy termination without trusting arbitrary forwarded headers.

Serve exactly the current master key bytes as an attachment with `Cache-Control: no-store`. No settings schema contains the key. Implement a narrow existing-master-key export exception beside the Fields secret-response rule in `.agents/skills/api-design/SKILL.md`, as the API-contract specification requires for intentional departures. The exception names only `GET /master-key-downloads`, authorized by a token issued through `POST /master-key-exports`, and permits that root-admin attachment download only after recent purpose-bound identity confirmation, with expiring single-use authorization, no-store and secret-free audit; it does not permit exporting saved storage/database/notifier secrets or embedding the key in JSON. Document the same exception in the contract and security architecture. This is the one necessary agent-instruction convention change in this feature. Audit proof issuance/export and acknowledgment without proof, token or key values. A keyed acknowledgment is stored by a hash identifying the current key; a download does not set it automatically.

Alternative rejected: a raw key in settings, a reusable signed URL, or a normal `ADMIN` check exposes the instance's decryption root. Requiring SMTP for all exports would unnecessarily block password owners on offline installations; adding new OAuth reauthentication flows is unnecessary with the host-file fallback.

### 7. Use one protection state with independent mail delivery

Persist `NOT_CONFIGURED`, `INITIALIZING`, `HEALTHY`, `PARTIAL`, `FAILED`, `OVERDUE`, `STOPPED` and `RESUMING` as Databasus backup health, with per-target detail. Per destination, persist `outstandingDueAt`, the earliest due schedule occurrence not covered by a successful copy with `snapshotAt >= outstandingDueAt`. Its fixed overdue deadline is `outstandingDueAt + 15 minutes`. New cron occurrences, polls, retries and schedule edits do not advance or erase it. On successful delivery, cover all occurrences up to that copy's snapshot time; choose the earliest later already-due occurrence as the new outstanding one, or leave none until the next due time. A stale snapshot delivered late cannot satisfy a newer occurrence. Schedule edits affect only future occurrences while an outstanding deadline remains. With a five-minute schedule and no successful backup from 12:00, the checker reports overdue at 12:15, not 15 minutes after an endlessly moving latest occurrence.

The checker does not require a failure callback. Configuration writes that remove the last destination create a stopped Databasus backup incident in that same transaction, irrespective of database counts or setup deferral. Configuring the first destination requests a run and starts initializing/resuming; at least one fresh successful copy ends stopped protection, while remaining failed destinations retain partial protection.

Store incidents and mail-attempt timestamps in the module. A background job sends through `mailer.Sender` to the current root-admin email, checking `IsConfigured` and a syntactically usable recipient first. Different symptom updates of one unresolved incident do not generate an email per retry; accepted reminders are at most daily. Failed sends retry exponentially from one minute to one hour, with safe last-error state. A first send becomes eligible when previously missing SMTP/address is supplied. Resolve obsolete pending mail before dispatch. Exactly-once SMTP delivery is not promised after a crash between acceptance and recording it.

Floating notices always reflect active problems, even when SMTP accepted mail. Initial setup reminders alone wait for any user database or storage anywhere in the instance, can be deferred for 24 hours and are suppressed while the settings section is visible. A new stopped incident overrides setup deferral. SMTP absence is its own inline configuration hint and links to the existing mail-server heading; SMTP settings remain operator-owned. Automatic incident mail is suspended during recovery pause.

Alternatives rejected: workspace notifiers require another selection/permission flow; email-only warnings disappear when SMTP fails; alerts emitted only by a failed job miss jobs that never started; email on every attempt floods the owner.

## Risks / Trade-offs

- Shared storage editors can redirect future encrypted Databasus backup files or make older copies unreachable -> preserve this explicitly accepted policy, explain it during selection and let the owner use an ordinary private workspace. API access to the key and archive remains root-only.
- An encrypted staging file consumes disk proportional to catalog size -> produce only one archive at a time, check space, fail visibly, bound retention of temporary files and clean interrupted spools. Never stage plaintext.
- Database publication and key installation are separate operations -> journal and gate normal startup until a matching pair is fully published; test interruption in every publication phase.
- UI import replaces live accounts and disconnects the current browser -> require current-root proof and explicit replacement confirmation, enforce complete quiescence, reinitialize without a container restart policy, and require sign-in with restored credentials.
- Recovery inputs contain the decryption key and may be large -> stream into private bounded staging, require HTTP acknowledgment before transfer, expire unconfirmed imports and remove staged keys without logging or returning them.
- A completion marker could disappear with imported history or be overwritten by a UI recovery -> keep startup-consumption records outside the snapshot and check them before archive-version/target-eligibility rules on later ordinary starts.
- An automatically initialized target can resemble an installation with user state -> recognize only an explicit initialization baseline, refuse unknown content and recheck under exclusive lifecycle access before replacement. A sole root account or non-default persisted setting already requires confirmed UI import.
- Exact release labels can be overridden by an operator, and development labels repeat -> check authenticated release and schema identity; document recovery only from trusted images/archives, not as a sandbox for attacker-supplied database dumps.
- Restored catalogs lag remote storage and discarded stale cleanup can leave objects behind -> expose snapshot time and local-storage validation, preserve only the claimed coverage, and document manual cleanup/reconciliation limits.
- Ordinary SMTP cannot guarantee unique delivery around a crash -> persist attempts, bound retry/reminder frequency and retain in-app state; do not promise exactly once.
- An entirely stopped process cannot report its own failure -> document external health monitoring separately without introducing it into this feature.
