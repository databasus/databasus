## ✨ Возможности

### 📦 **Типы бекапов**

- **Физические**: копия всего кластера базы данных на уровне файлов, построенная на нативном механизме инкрементальных бекапов PostgreSQL (подробнее)
  - **Полные**: самодостаточная копия кластера целиком
  - **Инкрементальные**: хранят только изменения с прошлого полного бекапа, поэтому остаются маленькими и быстрыми
  - **Стриминг WAL**: непрерывно захватывает поток записи базы и дает Point-in-time recovery (PITR). Сделан для аварийного восстановления с почти нулевой потерей данных
- **Логические**: нативный дамп базы в бинарном формате конкретного движка (со сжатием, пригоден для параллельного восстановления)

### 🔄 **Бекапы по расписанию**

- **Гибкое расписание**: каждый час, день, неделю, месяц или по cron
- **Точное время**: запускайте бекапы в нужный момент (например, в 4 утра, когда трафика мало)
- **Умное сжатие**: файл выходит в 4-8 раз меньше при сбалансированном сжатии (накладные расходы около 20%)

### 🧪 **Проверка восстановления** <a href="https://databasus.com/ru/restore-verification/">(документация)</a>

Databasus по-настоящему восстанавливает бекап, чтобы убедиться, что им можно пользоваться, а не просто сверяет контрольную сумму или наличие файла на диске.

- **Запуск**: после каждого бекапа или по гибкому расписанию (каждый час, день, неделю, месяц или по cron)
- **Настоящее восстановление**: поднимает контейнер с базой, восстанавливает бекап и сверяет размер восстановленной базы с исходным
- **Отчет**: перечисляет все таблицы с числом строк в каждой
- **Уведомления (необязательно)**: отправляйте отчет или только сообщения о сбоях через любой настроенный канал

### 🗑️ **Политики хранения**

- **По сроку**: держите бекапы фиксированное время (например, 7 дней, 3 месяца, год)
- **По количеству**: держите фиксированное число последних бекапов (например, последние 30)
- **GFS (дед-отец-сын)**: многоуровневое хранение — часовые, дневные, недельные, месячные и годовые бекапы хранятся независимо друг от друга, чтобы получить подробную историю за долгий срок (требование крупных компаний)
- **Ограничения по объему**: задайте лимит на размер одного бекапа и на суммарный объем хранилища

### 🗄️ **Разные хранилища** <a href="https://databasus.com/ru/storages/">(смотреть все)</a>

- **Локальное хранилище**: держите бекапы на своем VPS или сервере
- **Облачные хранилища**: S3, Cloudflare R2, Google Drive, NAS, Dropbox, SFTP, Rclone и другие
- **Безопасно**: все данные остаются под вашим контролем

### 📱 **Уведомления** <a href="https://databasus.com/ru/notifiers/">(смотреть все)</a>

- **Много каналов**: почта, Telegram, Slack, Discord, Teams, Mattermost, вебхуки
- **Мгновенно**: уведомления об успехе и о сбое
- **Для команды**: удобно встраивается в DevOps-процессы

### 🔒 **Безопасность корпоративного уровня** <a href="https://databasus.com/ru/security/">(документация)</a>

- **Шифрование AES-256-GCM**: защита файлов бекапов на корпоративном уровне
- **Хранилище с нулевым доверием**: бекапы зашифрованы и бесполезны для злоумышленника, поэтому их можно спокойно держать в общих хранилищах вроде S3, Azure Blob Storage и других
- **Шифрование секретов**: любые чувствительные данные шифруются и никогда не раскрываются, даже в логах и сообщениях об ошибках
- **Доступ только на чтение**: по умолчанию Databasus работает под read-only пользователем и не хранит ничего, что позволило бы изменить ваши данные
- **Двухфакторная аутентификация**: вход по паролю можно закрыть шестизначным кодом, который приходит на почту аккаунта. Вход через Google или GitHub по-прежнему опирается на проверки самих провайдеров

### 👥 **Подходит командам** <a href="https://databasus.com/ru/access-management/">(документация)</a>

- **Рабочие пространства**: группируйте базы, каналы уведомлений и хранилища по проектам или командам
- **Управление доступом**: решайте на уровне ролей, кто может смотреть и настраивать конкретные базы
- **Журнал аудита**: отслеживайте все действия в системе и изменения, которые сделали пользователи
- **Роли пользователей**: назначайте роль наблюдателя, участника, администратора или владельца внутри рабочего пространства
- **Логи через OpenTelemetry**: выгружайте логи приложения и журнал аудита во внешнюю систему (по умолчанию они еще и пишутся в локальный файл)

### 🎨 **Удобный интерфейс**

- **Интерфейс от дизайнера**: чистый и понятный, с вниманием к деталям
- **Темная и светлая темы**: выбирайте, что вам приятнее
- **Адаптив для мобильных**: проверяйте бекапы откуда угодно и с любого устройства

### 💾 **Поддерживаемые базы данных**

- **PostgreSQL**: 14, 15, 16, 17 и 18 (физические и логические)
- **MySQL**: 5.7, 8.0, 8.4, 9 и 26 (только логические)
- **MariaDB**: 5.5, 10, 11, 12 и 13 (только логические)
- **MongoDB**: 4.2+, 5, 6, 7, 8 и 9 (только логические)

### 🐳 **Self-hosted и безопасно**

- **На Docker**: просто развернуть и просто обслуживать
- **Приватность в приоритете**: все данные остаются на вашей инфраструктуре
- **Open source**: лицензия Apache 2.0, каждую строчку кода можно прочитать
- **Встроенный SSH**: подключайтесь к своему Databasus через SSH-туннель

## 📦 Установка

Установить Databasus можно четырьмя способами: скриптом установки (рекомендуется), обычным docker run или через Docker Compose.

### Вариант 1: скрипт установки (рекомендуется, только Linux)

Скрипт установки:

- ✅ Поставит Docker с Docker Compose (если их еще нет)
- ✅ Развернет Databasus
- ✅ Настроит автозапуск после перезагрузки системы

```bash
sudo apt-get install -y curl && \
sudo curl -sSL https://raw.githubusercontent.com/databasus/databasus/refs/heads/main/install-databasus.sh \
| sudo bash
```

### Вариант 2: обычный docker run

Самый простой способ запустить Databasus:

```bash
docker run -d \
  --name databasus \
  -p 4005:4005 \
  -v ./databasus-data:/databasus-data \
  --restart unless-stopped \
  databasus/databasus:latest
```

_Тот же образ лежит в реестре GitHub: возьмите `ghcr.io/databasus/databasus:latest`, если Docker Hub ограничивает вам скачивание._

Одна эта команда:

- ✅ Запустит Databasus
- ✅ Сохранит все данные в каталог `./databasus-data`
- ✅ Поднимет сервис автоматически после перезагрузки системы

### Вариант 3: Docker Compose

Создайте файл `docker-compose.yml` с такой конфигурацией:

```yaml
services:
  databasus:
    container_name: databasus
    image: databasus/databasus:latest
    ports:
      - "4005:4005"
    volumes:
      - ./databasus-data:/databasus-data
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "databasus", "healthcheck"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 60s
```

Затем запустите:

```bash
docker compose up -d
```

### Вариант 4: Kubernetes через Helm

Для Kubernetes ставьте прямо из OCI-реестра.

_Добавьте `--set image.repository=ghcr.io/databasus/databasus` к любой команде ниже, чтобы скачать образ из GHCR, а не из Docker Hub._

**С ClusterIP и port-forward (разработка и тесты):**

```bash
helm install databasus oci://ghcr.io/databasus/charts/databasus \
  -n databasus --create-namespace
```

```bash
kubectl port-forward svc/databasus-service 4005:4005 -n databasus
# Access at http://localhost:4005
```

**С LoadBalancer (облачные окружения):**

```bash
helm install databasus oci://ghcr.io/databasus/charts/databasus \
  -n databasus --create-namespace \
  --set service.type=LoadBalancer
```

```bash
kubectl get svc databasus-service -n databasus
# Access at http://<EXTERNAL-IP>:4005
```

**С Ingress (доступ по домену):**

```bash
helm install databasus oci://ghcr.io/databasus/charts/databasus \
  -n databasus --create-namespace \
  --set ingress.enabled=true \
  --set ingress.hosts[0].host=backup.example.com
```

Остальные варианты (NodePort, TLS, HTTPRoute для Gateway API) описаны в [README чарта Helm](../../deploy/helm/README.md).

## 🚀 Использование

1. **Создайте первую учетную запись**: перейдите на `http://localhost:4005` и зарегистрируйтесь. Первая учетная запись, созданная на инстансе, им и управляет
2. **Добавьте первую базу для бекапа**: нажмите "New Database" и пройдите мастер настройки
3. **Настройте расписание**: выберите интервал — каждый час, день, неделю, месяц или cron
4. **Укажите подключение к базе**: введите учетные данные и параметры соединения
5. **Выберите хранилище**: решите, где хранить бекапы (локально, S3, Google Drive и так далее)
6. **Настройте политику хранения**: по сроку, по количеству или GFS — так вы определите, сколько бекапы живут
7. **Добавьте уведомления** (необязательно): почта, Telegram, Slack, Mattermost или вебхук
8. **Сохраните и запустите**: Databasus проверит настройки и начнет делать бекапы по расписанию

### 🔑 Сброс пароля <a href="https://databasus.com/ru/password/">(документация)</a>

Если нужно сбросить пароль, воспользуйтесь встроенной командой:

```bash
docker exec -it databasus ./main --new-password="YourNewSecurePassword123" --email="owner@example.com"
```

Замените `owner@example.com` на настоящий адрес почты учетной записи, которой меняете пароль.

Если вы не помните, какой адрес управляет инстансом, выведите список учетных записей администраторов:

```bash
docker exec -it databasus ./main --list-admins
```

В выводе перечислены все учетные записи администраторов с их email, именем, датой создания и состоянием активности, а та, которую инстанс считает своим администратором, отмечена отдельно. Пароли и их хеши не выводятся.

Чтобы завести учетную запись без регистрации в браузере, например из скрипта деплоя, создайте ее из консоли:

```bash
docker exec -it databasus ./main --create-user --email="ops@example.com" --password="YourSecurePassword123" --role=admin
```

`--role` принимает `admin` или `member`, пароль должен быть не короче 8 символов, а `--name` задает отображаемое имя, если оно нужно. На инстансе, где еще нет ни одной учетной записи, первая должна создаваться с `--role=admin` и станет администратором инстанса. Повторный запуск для той же учетной записи ничего не меняет, поэтому команду можно выполнять при каждом деплое; пароль меняйте через `--new-password`.

### 💾 Бекап самого Databasus

После установки стоит еще и <a href="https://databasus.com/ru/faq/#backup-databasus">забекапить сам Databasus</a> или, как минимум, скопировать секретный ключ шифрования (это займет 30 секунд). Тогда вы сможете восстановиться из своих зашифрованных бекапов, даже если потеряете доступ к серверу с Databasus или он выйдет из строя.

## 🛡️ Инженерия безопасности и надежности

Databasus работает с чувствительными данными, поэтому предотвращение уязвимостей, несанкционированного доступа и утечек — одна из главных задач. Мы вкладываемся в это с обеих сторон системы: в самом коде (проверки прав, шифрование, аккуратное обращение с секретами) и в инфраструктуре вокруг него (анализ зависимостей, реакция на CVE, практики DevSecOps). Конвейер ниже автоматически запускается на каждом коммите и PR. Ни один слой сам по себе не закрывает все, но вместе они снижают шанс, что в релиз попадет уязвимый код, небезопасные зависимости, сломанные образы или невосстановимые бекапы.

Статический анализ идет в нескольких независимых проходах. CodeQL сканирует всю кодовую базу на проблемы безопасности. В каждом PR gitleaks ищет утекшие секреты, а semgrep проверяет код по правилам безопасности. У Dockerfile и CI-процессов есть свои дополнительные правила (закрепленные ссылки на actions, минимальные привилегии, подозрительные базовые образы), так что небезопасные паттерны отлавливаются еще до попадания в основную ветку. Поверх этих проверок на каждый PR Codex Security от OpenAI регулярно проводит более глубокие аудиты всей кодовой базы. Это отдельная программа, которая ловит архитектурные и сквозные проблемы, недоступные узким проверкам на уровне PR.

Со стороны зависимостей Dependabot сверяет все, что мы используем, с GitHub Advisory Database и показывает CVE уже через несколько минут после публикации. Обновления проходят через период выдержки, чтобы только что выпущенные версии успели созреть, прежде чем мы их примем. Это осознанная защита от инцидентов с зараженными пакетами вроде атак на цепочку поставок. Dependency Review Action сразу блокирует любой PR, который приносит новую CVE уровня HIGH или CRITICAL. В коде на Go govulncheck не пропускает PR, если наш код вызывает функцию с известной уязвимостью, а `go mod verify` сверяет каждый скачанный модуль с записанной контрольной суммой.

Образы контейнеров сканируются Trivy при каждой сборке. Отдельный проход Trivy по Dockerfile ловит ошибки конфигурации до того, как они попадут в образ. Все GitHub Actions закреплены на полные SHA коммитов, а не на плавающие теги вроде `@v4` или `@main`, которые в 2025 году были активным вектором атак. Процессы по умолчанию работают с минимальными привилегиями и расширяют их для отдельных задач только при реальной необходимости.

Критичные пути покрыты и юнит-, и интеграционными тестами, которые гоняются на настоящих контейнерах баз данных для каждой поддерживаемой СУБД и мажорной версии. Восстановление — самый важный путь для инструмента резервного копирования, поэтому мы тестируем его явно: каждый PR прогоняет полные циклы «бекап, затем восстановление» на тех же настоящих контейнерах и проверяет, что бекапы действительно восстанавливаются от начала до конца, а не просто успешно записались. Остальной конвейер CI/CD запускает линтер, проверку типов, полный набор тестов, smoke-тесты образов и мультиархитектурные сборки на каждом PR. Релиз выходит, только если все это прошло.

Нашли уязвимость? Сообщите о ней через вкладку Security на GitHub, см. [SECURITY.md](https://github.com/databasus/databasus?tab=security-ov-file#readme). Сообщения об уязвимостях мы разбираем в первую очередь. Про безопасность самого приложения в работе (AES-256-GCM на диске, хранилище с нулевым доверием, шифрование секретов, read-only пользователь базы по умолчанию) читайте в разделе [Безопасность корпоративного уровня](#-безопасность-корпоративного-уровня-документация) выше.
